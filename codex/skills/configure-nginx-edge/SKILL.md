# Configure NGINX Edge

1. Establish the requested edge behavior, authority, environment, NGINX distribution and exact version, compiled or dynamic modules, process manager or container runtime, config root and include graph, listener ownership, upstream protocol, traffic and payload profile, security boundaries, availability target, and acceptance evidence. Do not assume `/etc/nginx`, a module, certificate path, reload mechanism, or permission to change a running service.
2. Follow project fit and file naming. Preserve the detected vendor or repository topology, include order, environment overlays, site naming, template source, generated-versus-retained boundary, and deployment mechanism. Inspect the fully rendered configuration rather than one fragment. Do not flatten includes, rename host files, or introduce a universal `conf.d` layout merely for consistency.
3. Treat hostnames, paths, variables, headers, maps, certificate material, upstream responses, and generated config as untrusted data. Do not interpolate unchecked user or repository content into directives. Keep private keys and credentials out of tracked files, images, logs, diffs, and validation output. Use a least-privilege runtime identity and minimal filesystem and network access.
4. Define routing before directives. Specify listener and protocol, server-name selection, location precedence, URI normalization and rewrite behavior, static versus proxied ownership, upstream identity, method and body limits, error handling, and default or unmatched behavior. Read [NGINX routing and proxying](references/routing-proxy.md) only when these paths are affected.
5. Configure TLS from the actual termination and certificate-management contract. Define supported protocol and cipher policy from current platform requirements, certificate chain and key access, redirects, HSTS ownership, OCSP or stapling where supported, client certificates where required, and upstream TLS verification. NGINX configuration does not authorize certificate issuance, DNS changes, or secret installation.
6. Configure proxy headers, host and client-address trust, connection reuse, request and response buffering, streaming, WebSocket upgrades, retries, cache keys and bypass, cacheability, stale behavior, rate or connection limits, and timeouts explicitly. Read [TLS, cache, and runtime control](references/tls-cache-runtime.md) only for those concerns. Do not cache private or personalized responses under a shared key.
7. Make the smallest complete config change. Preserve unrelated routes and includes. Do not add a new proxy tier, module, cache, shared map, global directive, or generalized template without a current requirement. Account for memory, temporary disk, file descriptors, connection limits, upstream saturation, slow clients, and log volume under the representative workload.
8. Validate without changing runtime state. Render templates using the project-native path, inspect secret placeholders and includes, run the exact installed NGINX syntax and configuration test against the intended root, and test routing in an isolated container or environment where available. A successful syntax test does not prove certificate access, DNS, upstream reachability, routing, cache safety, or reload success.
9. Prepare rollout and rollback before any runtime action. Capture the exact prior immutable configuration or artifact, target instances, health checks, connection-drain behavior, staged order, stop thresholds, reload or restart command, and rollback command. Confirm the literal target and authorization immediately before reload or restart. Never use production traffic as a configuration probe.
10. For an authorized rollout, apply only the reviewed artifact, use graceful reload where supported, observe process and worker health, active connections, upstream failures, status classes, latency, cache results, TLS handshakes, and logs, then exercise representative routes. Roll back on the predefined threshold or ambiguous partial state.
11. Inspect the full owned diff and rendered config. Verify routing, header trust, TLS, proxy, cache, timeout, streaming, limits, logging redaction, and rollback evidence. Report passed, failed, skipped, unavailable, and inconclusive gates.

Finish when the exact rendered configuration passes the installed validator, isolated behavior matches the routing and security contract, and any authorized runtime change has health and rollback evidence without exposing secrets.
