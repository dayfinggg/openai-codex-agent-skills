# Build Backend APIs

1. Establish the requested consumer-visible behavior, authority, protocol, supported clients, compatibility policy, trust boundaries, data classification, latency and availability targets, rate and payload expectations, and acceptance evidence. Inspect the closest repository instructions, manifests, lockfiles, framework and runtime versions, route registration, middleware order, schemas, callers, generated clients, tests, and deployment constraints. Do not infer an endpoint, field, status, privilege, or external side effect that the requirement does not define.
2. Follow project fit and file naming. Preserve the detected framework topology, route discovery, controller or handler naming, dependency injection, module ownership, public package exports, schema generation, and test placement. Inspect neighboring files of the same role before adding one. Do not impose a generic controllers-services-repositories layout, rename public paths, or hand-edit derived clients and schemas.
3. Define the API contract before implementation. For HTTP, read [HTTP and OpenAPI](references/http-openapi.md) only when method, status, headers, caching, pagination, idempotency, error, or OpenAPI behavior is affected. For GraphQL, read [GraphQL contracts](references/graphql.md) only when the schema or resolver boundary is affected. For another protocol, use its exact-version primary specification and local definitions.
4. Define each input boundary, authentication context, authorization decision, ownership check, tenant scope, validation and normalization, size and complexity limit, and stable failure shape. Parse untrusted data into a validated internal representation. Keep authentication distinct from authorization and verify access at the object or action boundary, not only in routing middleware.
5. Implement the smallest complete handler and service path. Preserve public names, defaults, ordering, nullability, errors, side effects, and generated contracts unless the change explicitly evolves them. Do not add a new framework layer, generic base handler, repository abstraction, dependency, versioning scheme, or feature flag without a current consumer and evidence that local mechanisms are insufficient.
6. Make transport semantics explicit. Choose method or operation, status, media type, conditional request, cache policy, pagination cursor, sorting, and idempotency behavior from the contract. Use stable machine-readable errors without stack traces, secrets, internal queries, or sensitive identifiers. Do not return success before a required durable effect is established.
7. Bound remote and data work. Propagate cancellation and deadlines where supported, set request and response size limits, bound concurrency, queries, batches, queues, and retries, and release streams, files, sockets, and transactions. Retry only documented transient operations that are safe to repeat. Coordinate data invariants and transactions with the relevant database skill.
8. Apply boundary-specific security and performance controls. Parameterize queries, constrain dynamic fields and sorts, encode output for its actual context, protect browser state-changing flows against CSRF where relevant, configure CORS narrowly, prevent SSRF through destination validation, and rate-limit abuse-sensitive actions. Use `secure-web-application-boundaries` for a full threat model or appsec assessment and `validate-system-performance` for system load evidence.
9. Treat API calls, queues, email, payments, webhooks, and third-party mutations as external writes. Use fakes or authorized test environments for verification. Do not trigger production effects, create real accounts, send messages, charge money, or publish schemas without explicit authorization. Preserve idempotency keys and audit evidence for authorized consequential actions.
10. Verify at the cheapest reliable boundaries. Run configured formatting, static analysis, type or compile, schema validation or diff, focused unit and integration tests, authorization and invalid-input cases, contract and generated-client checks, cancellation and timeout paths, and representative query or latency evidence. Exercise the real route stack when middleware or serialization matters.
11. Inspect the full owned diff, generated artifacts, and public contract. Remove unrelated cleanup and report passed, failed, skipped, unavailable, and inconclusive gates with compatibility or security consequences.

Finish when supported consumers can exercise the documented contract, unauthorized and invalid requests fail safely, resources and side effects remain bounded, compatibility is accounted for, and every material completion claim has observed API evidence.
