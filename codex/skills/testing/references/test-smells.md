For each new test, identify the observable promise and a plausible wrong implementation that would make it fail. If neither is clear, revise or omit the test. Obtain expected results from a specification, a worked literal example, or an independent trusted oracle. A green suite and high coverage alone do not establish discrimination against wrong behavior.

- Reject assertions that reproduce the implementation's algorithm, compare a value to itself, or read the same constant on both sides. Prefer independently justified expected values or complementary invariants.
- Reject tests that mock the subject under test or replace all meaningful collaboration. Use real internal modules. Use boundary stubs for controlled external outcomes, fakes for realistic state, spies or mocks only when the interaction itself is contractual. Keep doubles faithful to the real boundary and verify integration separately when that boundary changed.
- Avoid private-method tests and incidental call-order or call-count assertions. Observe return values, errors, output, or durable effects through a supported interface. Inspect persistence directly only when storage is the contract or the integration boundary under test. Do not force a new public API just for testing.
- Require a meaningful assertion or explicit exception/interaction expectation. A call followed by successful termination proves only absence of an observed crash, which is insufficient for a promised value, state change, or rejection.
- Await asynchronous work and assertion promises, and check that exception expectations encompass the operation that should fail. Reject catch-all handlers that swallow unexpected failures and tests that return before callbacks or background effects occur.
- Cover relevant failure and boundary cases when behavior changes there. A success-only test does not establish rejection, cleanup, rollback, cancellation, retry, or isolation guarantees. Do not invent unrelated failure requirements.
- Avoid assertions on unspecified ordering, wall-clock timing, unstable snapshots, and shared mutable fixtures. Control time and randomness at boundaries, reset state, use bounded synchronization rather than blind sleeps, and preserve numerical tolerances justified by the contract.
- Do not bulk-write tests for imagined interfaces before running the first red-green slice. Do not approve snapshots merely because the tool generated them. Inspect their promised behavior.
- Do not delete failing assertions, add unconditional skips, mark a new regression expected-to-fail, suppress health checks, or widen tolerances merely to obtain green output. Diagnose whether the implementation, fixture, or requirement is wrong.

When reviewing rather than implementing, report demonstrated defects with their affected behavior and evidence. Set severity from the actual consequence, not a fixed label attached to a smell. Keep a weaker but valid test distinct from a vacuous one, and do not classify stylistic preferences as defects.
