Use the existing property library. Choose a property only when its domain and guarantee come from the requested contract. Common candidates include roundtrips or inverses, idempotence, independent reference equivalence, conserved state, ordering plus permutation preservation, commutativity, associativity, and identity. No universal strength ordering exists. Two mutually wrong encoder/decoder functions can pass a roundtrip, so add a known-format example when interoperability is the promise. A no-crash check alone rarely justifies adding a dependency.

1. Inspect the observable boundary before deciding no property exists. For mixed I/O and calculation, test an existing pure operation or record before/after state through the contract. Copy inputs before mutation when necessary. Do not add an inverse, change a public signature, or restructure production code solely to obtain an algebraic property without authorization. Propose a specific necessary seam change only when existing interfaces cannot verify the requested behavior.
2. Generate valid inputs directly. Bound numeric domains, text alphabets, and collection sizes to the contract. Derive dependent fields together. Use filtering or assumptions only for constraints that cannot reasonably be generated. Never suppress excessive-rejection or unsatisfiable-input health checks just to pass.
3. Pin known boundaries with explicit examples or parameterized regression cases. Choose only meaningful empty, singleton, duplicate, zero, extreme, Unicode, and malformed-input cases. For invalid data, assert the documented rejection and allow unexpected exceptions to fail.
4. Assert a real relation that can disagree with a wrong implementation. Checking only length misses incorrect order or content. Repeated calls can test promised determinism when nondeterminism is possible, but comparing a stored result with itself cannot. Use justified tolerances for floating-point contracts and avoid unspecified map/set ordering.
5. Start with the project's settings. Set a bounded case and input-size budget suitable for the operation. Change deadlines or sample counts only for an observed workload need. Keep a process deadline even when per-example timing is disabled. Reset external and mutable state for each generated example. In Hypothesis, a pytest function-scoped fixture is reset per test, not per generated example.
6. On failure, retain the minimized counterexample and available seed or replay information. Reproduce it with the same version and configuration before fixing. Preserve intentional durable regression examples according to project convention. Proptest replays persisted failures from `proptest-regressions` before fresh cases. Do not treat these intentional regression inputs as disposable scratch output.
7. Classify the result against the external specification, documented preconditions, types, and existing contract tests. An in-domain violation is an implementation defect. An out-of-domain input needs a constrained generator. A contradicted guarantee needs a corrected property. An unresolved edge contract needs a maintainer decision. Do not infer a guarantee from a function name alone or silently discard ambiguous counterexamples.
8. Inspect executed examples, rejection or health-check errors, and final runner results. Passing generated samples establish only the tested property and domain. Retain the failing input as a focused regression after the fix where the framework's normal persistence is insufficient.

For Python, consult [Hypothesis 6 API and health checks](https://hypothesis.readthedocs.io/en/latest/reference/api.html) for generators, explicit examples, filtering, and fixture semantics, and [settings](https://hypothesis.readthedocs.io/en/latest/tutorial/settings.html) when changing budgets. For Rust, use the installed [proptest 1 API](https://docs.rs/proptest/latest/proptest/) and [failure persistence](https://proptest-rs.github.io/proptest/proptest/failure-persistence.html). Run these properties with the project's normal pytest or Cargo test command.

For existing Solidity invariant tests, distinguish global invariants over reachable transaction sequences from operation assertions. Cover relevant solvency, supply conservation, access, or conversion promises only when they are the changed contract. Reject compiler-guaranteed unsigned bounds as vacuous properties and inspect reachable-state coverage. Keep the project's Echidna or Medusa choice and verify that installed tool's current invariant-function rules before editing. Do not impose one fuzzer's signature or mutability rules on another mode.
