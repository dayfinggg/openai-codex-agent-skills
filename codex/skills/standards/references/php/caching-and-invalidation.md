# Caching and invalidation

- Cache measured expensive work or an explicit product requirement. Define the authoritative data, allowed staleness, invalidation event, capacity, and failure behavior before choosing a store. Do not use a cache as the only durable record.
- Reuse the installed framework's cache abstraction. PSR-6 suits item/pool operations; PSR-16 suits simple key/value operations. Check the installed interface major and adapter PHP requirements before changing signatures or packages.
- Include tenant, locale, relevant authorization scope, query inputs, and payload schema version in keys where they affect the value. Never share user-specific results under a public key. Hash sensitive key inputs when appropriate and avoid logging raw credentials or personal data.
- Respect portable key restrictions and backend limits. Store a validated, versioned data payload rather than live ORM entities or service objects. A deployment must tolerate old entries or invalidate them deliberately.
- Choose TTL from acceptable staleness. Under PSR-16, zero or negative TTL deletes an item, while `null` uses the configured default and may mean no expiration. Do not assume Redis or a framework uses identical TTL units or conventions.
- Distinguish a miss from cached `false`, zero, empty strings, and null. PSR-6 exposes `isHit()`; PSR-16 cannot distinguish cached null from a null miss using the default alone. Use an explicit payload envelope or appropriate abstraction when that distinction matters. Avoid `has()` followed by `get()` as an atomic existence check.
- Invalidate or update after a successful database commit. A racing reader may repopulate an old value after deletion. Where stale reads are unacceptable, use a tested version/locking strategy or avoid caching that decision. A TTL alone does not establish consistency.
- Use a framework's documented stampede protection when concurrent misses overload the source. Bound lock wait and ownership, and allow expiry only with understood consequences. Stale-while-revalidate is appropriate only if serving stale data is acceptable. Add TTL jitter when synchronized expiry is a demonstrated load risk.
- Treat rate limits, deduplication, and security decisions separately from best-effort result caching. Choose fail-open or fail-closed behavior from the actual contract. An atomic database constraint may be necessary even when a cache lock exists.
- Bound cache timeouts. For an ordinary result cache, decide whether source fallback is safe under outage load. Never hide every backend exception or retry indefinitely. Keep bulk clears scoped to the application/tenant namespace.
- Test hit, miss, expiration, invalidation, cached empty values, tenant isolation, deployment payload changes, concurrent refresh, and backend failure where relevant. Measure latency, hit ratio, eviction, refresh errors, and source load without unbounded metric labels.

Sources: [PSR-16](https://www.php-fig.org/psr/psr-16/), [PSR-6](https://www.php-fig.org/psr/psr-6/), and [Symfony Cache](https://symfony.com/doc/current/cache.html). Framework-specific locks, tags, and refresh behavior require the installed version's documentation.
