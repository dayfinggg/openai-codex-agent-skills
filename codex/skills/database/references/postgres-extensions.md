Inspect pg_extension.extversion, PostgreSQL major, provider restrictions, and existing extension-owned objects before choosing APIs. Keep ordinary PostgreSQL unless the task selected an extension. Do not install an extension, remove constraints, or change retention merely because a reference proposes it.

For PostGIS, establish the actual SRID, coordinate order, geometry/geography semantics, required units, dimensionality, validity, and error tolerance. Do not relabel coordinates with an SRID when a transformation is required. Preserve stored precision and repair invalid geometries only as an authorized data change. Select an index supported by the actual type/operators and confirm its plan, rather than indexing every spatial column. For distance filtering, ST_DWithin can use a spatial index and uses CRS units for geometry and meters for geography. Validate longitude/latitude order and boundary behavior. See [PostGIS 3.6 ST_DWithin](https://postgis.net/docs/manual-3.6/ST_DWithin.html). Select the matching released manual from [PostGIS documentation](https://postgis.net/documentation/), since the unversioned docs may describe a development build.

For pgvector, establish the embedding model, dimensions, normalization, stored type, distance operator, and matching operator class. Preserve vector/halfvec/bit casts and dimensional consistency. Test NULL and zero-vector behavior for the chosen distance, ingestion timing, and parameter binding. Compare approximate results with an exact baseline on authorized data. Filtered approximate scans may return fewer rows because filtering follows ANN scanning. A separate B-tree does not guarantee prefiltering inside ANN. In pgvector 0.8+, inspect iterative-scan support and limits when recall after filtering is inadequate. Test recall, ordering, latency, and tenant isolation together. Choose HNSW/IVFFlat, quantization, build timing, and memory from workload evidence, not fixed dimension or row-count recipes. Match the installed tag's README in the [official pgvector repository](https://github.com/pgvector/pgvector).

For hybrid search, preserve keyword language/configuration, vector model, filter scope, and required exact-match behavior in both candidate branches. Inspect both plans and deduplicate by stable row identity. Compare candidate recall and final ranking before altering fusion weights, limits, or reranking. Do not install BM25/pgvectorscale or force planner settings by default. Use the selected extension's versioned documentation and [PostgreSQL 18 text search](https://www.postgresql.org/docs/18/textsearch.html) for built-in search.

For TimescaleDB, establish its exact version and whether the workload actually benefits from time partitioning. Compare authorized plans, ingest/update patterns, time filters, chunk pruning, storage, and existing policies. Confirm the time column and key/FK compatibility. Unique indexes must include all partitioning columns. Do not weaken global uniqueness or drop FKs to force conversion. Obtain a decision if the requested conversion cannot preserve these contracts. See [hypertable uniqueness](https://www.tigerdata.com/docs/build/performance-optimization/hypertables-and-unique-indexes) and choose the installed TimescaleDB release's API from [the documentation](https://www.tigerdata.com/docs/).

Choose chunk interval, columnstore/compression segment/order keys, continuous-aggregate refresh windows, and retention from the actual access and update patterns. Unknown retention is a missing decision, not permission to delete data. Match older compression versus newer columnstore APIs to the installed version. Rehearse in-place or shadow-table conversion according to lock, volume, concurrent-write synchronization, and restoration requirements. Validate copied identities/values, chunks, indexes, constraints, continuous aggregates, jobs, compression state, and query plans before cutover. Keep the old table until verification and rollback conditions permit removal. Do not claim a fixed compression ratio or speedup without measurement.
