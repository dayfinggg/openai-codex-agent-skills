1. Inspect the application's actual filters, sorts, projections, pagination and updates before proposing a model or index. Build a workload inventory from callers and available query statistics or bounded slow logs, including frequency, latency, cardinality, growth, read/write mix and critical infrequent operations. Use Atlas tools only when available for the authorized deployment. Check edition, tier and version before relying on diagnostic features. MongoDB 9.0 query statistics can include sampled writes, so do not assume read-only or complete workload coverage. See [9.0 release notes](https://www.mongodb.com/docs/manual/release-notes/9.0/).

2. Inspect collection metadata, validators, indexes and small projected samples. Record BSON types, optional and missing fields, arrays, relationship cardinality, document-size distribution and tenant predicates. Sampling does not establish that every document has the sampled shape. Separate query correctness from performance recommendations.

3. Design documents around co-access and update boundaries. Embed bounded data read together when its lifecycle and access policy match. Reference independently accessed entities, growing arrays, high-cardinality relationships or separately protected data. Do not copy relational tables mechanically or merge genuinely independent collections merely to reduce their count. Account for duplicate-update work and the BSON size limit of 16 MiB. Measure large documents and array fan-out rather than assigning arbitrary cardinality thresholds. Use [MongoDB 9.0 data modeling](https://www.mongodb.com/docs/manual/data-modeling/) and [limits](https://www.mongodb.com/docs/manual/reference/limits/).

4. Select a specialized model only for a demonstrated workload need. Keep these decision checks when replacing copied pattern examples.

- For hot/cold subsets or outliers, bound the embedded subset and preserve a complete, paginated overflow read path. Check concurrent overflow insertion and count/flag consistency.
- For attribute arrays or polymorphic collections, verify the actual attribute queries, multikey behavior, discriminator and per-type validation. Keep named fields where strict field contracts or search mapping need them.
- For time-based measurements, compare native time series with bounded custom buckets using time-range reads, metadata stability/cardinality, insertion rate, retention and required transaction/update support. Consult version-specific time-series restrictions before selecting it.
- For computed values or extended references, specify who refreshes every copy and the acceptable staleness. Do not copy sensitive fields across access boundaries. Approximation additionally requires explicit tolerance for lost unsynced increments after a crash. Never approximate exact financial, inventory or audit values.
- For archival, preserve retention exceptions, batch within load limits and verify the copied records and values before deleting their originals. TTL deletion is not archival. Keep historical reads available when the contract requires them.
- Distinguish historical document revisions from schema versions. Couple history/current writes transactionally when both must succeed together. Keep history retention consistent with audit requirements. For schema evolution, support mixed readers/writers, use conditional idempotent batches and check missing version fields, wrong types and version distribution. Introduce or tighten validators without unexpectedly rejecting existing supported writes.

Retrieve syntax only for the chosen model from [MongoDB 9.0 design patterns](https://www.mongodb.com/docs/manual/data-modeling/design-patterns/) and [schema validation](https://www.mongodb.com/docs/manual/core/schema-validation/). Do not install a catalog of example schemas.

5. Write the simplest query that preserves the requested meaning. Prefer find for filtering, sorting and projecting. Use aggregation for grouping, transformations or joins. Confirm BSON Date/ObjectId/numeric types, time boundaries, stable ordering and array semantics. Test null, missing and empty arrays independently. Do not replace an existence predicate with non-null matching unless that is the requested meaning. Use `$elemMatch` when conditions must match the same array member. Escape literal regex input and check GeoJSON longitude/latitude order. Require a text index before `$text`. Prefer native operators over `$where` or unnecessary `$expr`.

6. For performance work, capture the exact filter, sort, projection, limit, collation, parameters and explain plan. Start with queryPlanner. Execution statistics execute the query, so bound runtime and workload before collecting them. Inspect aggregate stages for `$out` or `$merge` before classifying an operation as read-only. Compare returned records, keys/documents examined, sort stages, memory/spills and runtime on comparable data. A collection scan can be appropriate for a small collection or low-selectivity query.

7. Derive candidate compound indexes from measured query shapes. Check equality/sort/range ordering, leading prefixes, multikey limits, collation, partial/sparse predicates and write/storage cost. Confirm coverage in explain rather than assuming every projected query is covered. An index matching case-insensitive collation does not by itself accelerate case-insensitive `$regex`. Index count alone is not a tuning target. See [MongoDB 9.0 compound indexes](https://www.mongodb.com/docs/manual/core/indexes/index-types/index-compound/) and [regex index behavior](https://www.mongodb.com/docs/manual/reference/operator/query/regex/).

8. Inspect every affected query and index constraint before removal. A zero-use observation is limited to its measurement interval and node, and can miss rare critical queries. Preserve unique, TTL, shard-supporting and otherwise required indexes. Use available Performance Advisor recommendations as evidence, not automatic authorization. For an authorized production removal, hide a supported candidate, observe a representative workload, unhide on regression, then drop only within the authorized plan. Hiding does not remove uniqueness, TTL effects or write overhead. See [MongoDB 9.0 hidden indexes](https://www.mongodb.com/docs/manual/core/index-hidden/).

9. For aggregations, move independent filters earlier only when their meaning survives the move. Check index use before transformations, join cardinality, foreign lookup indexes, group cardinality and array expansion. Avoid unwind/regroup when array expressions preserve the intended result more simply. Keep sort/limit optimizations semantically correct. Let the optimizer prune fields instead of adding speculative projections. Inspect actual per-stage and per-operation memory limits and spill policy for the installed release. Do not set allowDiskUse globally to hide an inefficient pipeline. See [MongoDB 9.0 aggregation optimization](https://www.mongodb.com/docs/manual/core/aggregation-pipeline-optimization/).

10. For updates, use targeted operators when changing selected fields and return a document only when the caller needs it. Preserve conditional filters, upsert identity, concurrency and retry semantics. Do not claim full replacements always produce full-document oplog entries. Verify the relevant driver/server behavior and observed cost instead.

11. For connection problems, inspect runtime, installed driver version, topology, client ownership, warm-instance reuse, app replica count, operation duration/concurrency and server connection limits. Reuse a supported long-lived client and close it at its lifecycle boundary, not after each request. Respect driver thread/process safety. Separate DNS/SRV, routing, TLS/auth and server-selection errors from checkout waits or slow operations. Do not change network access, read preference or timeouts merely to suppress an error.

12. Measure checkout wait/failure, in-use connections, creation/closure churn, operation latency and server capacity. Account for pools per client and contacted server, monitoring sockets and application instances. Distinguish connect, server-selection, checkout, operation and socket deadlines. Increase capacity only when measured waits and spare server capacity justify it. Do not copy fixed pool presets, per-connection memory estimates or one driver's monitoring formula into every language. Explain each changed setting using workload evidence. Driver syntax and lifecycle details belong in [driver documentation](https://www.mongodb.com/docs/drivers/). The verified example reference is [Node.js driver 6.x pools](https://www.mongodb.com/docs/drivers/node/v6.x/connect/connection-options/connection-pools/), not a universal driver contract.

13. Verify model/query changes with representative expected records and negative cases, supported old/new document shapes, tenant restrictions, relevant concurrent writes and size/growth boundaries. Compare affected plans and write cost after index changes. For pools, exercise reuse, concurrent checkout, timeout/error recovery and shutdown in the actual runtime. Preserve an available rollback for model, validator and index changes. Delete only task-owned test records within the authorized target.

14. Report the affected workload and resulting behavior, measured evidence and required migration/index rollout. State unsupported driver features or unavailable diagnostic sources precisely. A generated query that was not run remains unverified.
