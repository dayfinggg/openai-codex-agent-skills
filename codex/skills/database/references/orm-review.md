1. Trace the actual implementation and caller through query construction, execution/enumeration, materialization, persistence, and commit. Establish result identity, cardinality, ordering, random-page requirements, filters, generated keys, retries, domain events, audit/outbox writes, and partial-failure behavior. An interface name or iterator-shaped API does not prove streaming or bounded memory.
2. Capture generated SQL, bound parameter shape, round trips, returned rows, and representative plans where execution is authorized. Count hidden lazy loads, repeated enumeration, nested helpers, repeated flush/save calls, and immediate bulk writes. A load-mutate loop with one final save is not evidence of a save per row. Source-only review cannot prove missing physical indexes, full scans, or latency improvement.
3. Fix evidenced N+1 with bounded projections, explicit loading, or batching that preserves semantics. Compare join fan-out against split/select-in round trips and consistency. Do not globally eager-load every relation or suppress translation errors with an early unbounded materialization. Preserve complete exports while controlling buffering. Check tenant, soft-delete, authorization, and count filters in every generated query.
4. Check every pagination ordering key and direction, including a unique tie breaker and NULL ordering. A composite seek predicate is lexicographic, not independent inequalities on each field. Keep numbered-page access when required. Distinguish deterministic ordering from cross-request snapshot consistency. Test ties, empty and final pages, and relevant insert/delete changes. Check root identities after collection joins, not merely returned SQL row count.
5. Trace actual unit-of-work and transaction boundaries, including repository-hidden saves, bulk writes, raw SQL, and shared connections. Check atomicity with audit/outbox records, affected-row handling, token predicates and updates, and conflict retry behavior. A transaction does not synchronize stale tracked entities or make existence-check-then-insert race-safe. Preserve database uniqueness and durable replay identity/checkpoints. Chunking alone is not idempotency.
6. Compare expected identities and field values for relevant empty, NULL, duplicate, missing-relation, and ordering cases. Check SQL/query count, later-write rollback, and a competing writer where those paths change. Reject a benchmark expectation that contradicts the supplied domain contract rather than adjusting code to a faulty expected SQL.

For EF Core, use the installed EF/provider version. These sources cover the common relational workflow, while version-specific overrides require their documented minimum release.

- Trace IQueryable versus Enumerable operators, helpers, and enumeration to determine what executes remotely. Keep translatable filters and aggregates server-side. Preserve substring and collation semantics when improving index compatibility. Compilation helps only demonstrated hot translation overhead, not database I/O. Dynamic request values should not become a new expression/SQL shape per value. Keep default parameterization unless skew/plan evidence supports a documented override. See [efficient querying](https://learn.microsoft.com/en-us/ef/core/performance/efficient-querying) and [advanced performance](https://learn.microsoft.com/en-us/ef/core/performance/advanced-performance-topics).
- Read-only entity results may use no tracking. Scalar projections have no entity tracking to remove, while an entity nested in a DTO still can. Preserve tracking and identity behavior for later edits. Inspect actual mapping/migrations and FK index conventions before alleging absent coverage. See [tracking](https://learn.microsoft.com/en-us/ef/core/querying/tracking) and [indexes](https://learn.microsoft.com/en-us/ef/core/modeling/indexes).
- A second OrderBy replaces prior primary ordering. Reordering an already bounded materialized page is different from selecting an unordered page. Compare collection Include fan-out with split-query cost and consistency. See [pagination](https://learn.microsoft.com/en-us/ef/core/querying/pagination) and [split queries](https://learn.microsoft.com/en-us/ef/core/querying/single-split-queries).
- ExecuteUpdate/Delete, available from EF Core 7 with provider support, execute immediately, bypass tracked snapshots and SaveChanges hooks, and do not automatically apply concurrency tokens. Check predicates, token updates, affected rows, shared transaction scope, and stale tracked values before subsequent saves. See [bulk writes](https://learn.microsoft.com/en-us/ef/core/saving/execute-insert-update-delete) and [concurrency](https://learn.microsoft.com/en-us/ef/core/saving/concurrency).
- Do not overlap operations on the same DbContext, including through different repositories. Preserve disposal and cancellation. For growing imports, saved entities remain tracked. Repeated tracker scans may grow expensive. Clear or rotate only batch-owned contexts without pending changes. Add and AddRange do not automatically DetectChanges. Restore any temporarily changed detection setting in finally and detect required changes before persistence. See [DbContext lifetime](https://learn.microsoft.com/en-us/ef/core/dbcontext-configuration/) and [change detection](https://learn.microsoft.com/en-us/ef/core/change-tracking/change-detection).

For Doctrine ORM, establish ORM and DBAL versions together. The researched current 3.x documentation is 3.7, whose pagination API differs from 3.6. Consult the installed release before choosing Paginator versus OffsetPaginator/CursorPaginator. Collection fetch joins multiply SQL rows, so applying a raw limit need not select a full root-entity page. Preserve root identity and count semantics. Inspect emitted SQL rather than assuming one DQL query is one round trip. See [Doctrine 3.7 pagination](https://www.doctrine-project.org/projects/doctrine-orm/en/3.7/tutorials/pagination.html).

Trace flush boundaries and UnitOfWork state, including lifecycle listeners and bulk DQL paths. Explicitly include raw DBAL writes in the required transaction. On transaction failure, do not reuse a closed EntityManager or assume detached objects reverted with the database. Start a new unit of work for recovery. Preserve version checks across requests, and require a transaction for pessimistic locks. See [Doctrine 3.7 transactions and concurrency](https://www.doctrine-project.org/projects/doctrine-orm/en/3.7/reference/transactions-and-concurrency.html).

For SQLAlchemy, match the installed 2.x minor and driver. The researched current series is 2.1, with [2.0 documentation](https://docs.sqlalchemy.org/en/20/) retained for existing applications. Lazy relationship access can produce N+1. Select-in versus joined eager loading changes round trips and duplicate SQL rows, and collection joined loads require correct result uniquing. Preserve filtering and ordering around pagination. See [SQLAlchemy 2.1 relationship loading](https://docs.sqlalchemy.org/en/21/orm/queryguide/relationships.html).

Trace autoflush before queries, identity-map reuse, explicit commit, rollback, and object expiration. A read-looking ORM call may flush pending writes. After a flush failure, roll back the Session before reuse. Own one Session per thread and AsyncSession per task, and close it at the unit-of-work boundary. See [SQLAlchemy 2.1 sessions](https://docs.sqlalchemy.org/en/21/orm/session_basics.html). Check version_id_col and affected rows for concurrency, especially when bulk DML bypasses per-instance version checking. See [SQLAlchemy 2.1 version counters](https://docs.sqlalchemy.org/en/21/orm/versioning.html).
