1. Read the lockfile, package scripts, schema or contract, generator, config, adapter, and client imports. Establish CLI, client/ORM, driver, Node/runtime, and database versions together. Use the project-local pinned CLI through its package manager. Do not run floating prisma@latest or use a globally installed CLI to repair an existing project. Determine the actual target without printing connection strings.
2. Select the documentation matching that installed generation. The researched stable baseline is [Prisma ORM 7](https://www.prisma.io/docs/orm/v7). The [release-status page](https://www.prisma.io/docs/orm/release-status) describes ORM 8 as a release candidate even though bare installation can select it. Distribution tags are not stability guarantees. For installed ORM 8, read its package-owned prisma-8/SKILL.md and matching references if supplied, plus its release's official docs. Do not apply version 7 commands, generated-client setup, errors, or transactions to version 8 by analogy. If the package guidance is absent, use the selected release's official documentation, not an automatic upgrade.
3. Diagnose connection/runtime issues before any schema writes. Verify provider, environment loading, TLS, schema selection, pooler/direct endpoint roles, and adapter compatibility. Prisma 7 config does not implicitly load .env. Keep its explicit generated output/import path and compatible SQL driver adapter or Accelerate path. Accelerate URLs do not belong in ordinary driver adapters. Do not disable TLS verification to hide certificate errors. Keep application client lifetime appropriate to the runtime and avoid reconnect/disconnect per request. Read the [version 7 upgrade guide](https://www.prisma.io/docs/guides/upgrade-prisma-orm/v7) only when upgrading is requested.

The following are Prisma 7 command forms from the [version 7 CLI reference](https://www.prisma.io/docs/orm/v7/reference/prisma-cli-reference). Run them from the project directory with the repository's local CLI launcher and configured target, only when the step is authorized.

```text
prisma version
prisma validate
prisma generate
prisma migrate status
prisma migrate dev --create-only
prisma migrate deploy
```

Use validate for schema validation and generate for client artifacts, then run a real application query or test for the changed contract. Neither command proves connectivity or migration success. Generation is explicit after relevant Prisma 7 schema changes. Seeds are explicit writes and must not run just to test a connection.

Use migrate dev only on an authorized development database with its correctly isolated shadow database. Even --create-only can encounter drift and request reset. Stop on a reset request rather than accepting automatically. Review the draft SQL for rename-as-drop/add and unsupported database objects before applying it. Use deploy for authorized deployment of reviewed migrations, not dev or db push. Deploy does not prove drift absence, generate the client, or supply automatic down migrations. Follow the shared migration procedure for locks, compatibility, and restoration. See [customizing version 7 migrations](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/customizing-migrations).

Inspect the local command's help and version-matched reference before migrate diff, db execute, or resolve. Their options differ across majors. Diff output is a proposal, not authorization to execute it. db execute does not reconcile migration history. resolve changes history, not the physical schema or data. Inspect partial application before marking anything applied or rolled back. Preserve existing schema edits before db pull, using a non-overwriting inspection path when possible. db push has no migration-history safety and is not a production rollout substitute.

For destructive commands, retain [Prisma's AI checkpoint](https://github.com/prisma/prisma/releases/tag/7.9.0). Explain the actual target and data loss, obtain explicit consent for that action, and obey the installed tool's gate. Never fabricate consent, hide agent detection, or treat --force as authorization. If the installed tool requires PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION, pass only the user's exact applicable consent message. Do not infer consent from unrelated approvals. Do not expose Studio publicly or assume MCP provides a reset tool.

For client changes, capture emitted SQL and round trips using existing logging with sensitive values redacted. Trace nested relation reads and writes, relationMode, actual physical indexes/FKs, select/include payload, and provider-specific filter semantics. Database emulation of relations is not equivalent to enforced FKs. Parameterize raw SQL through supported tagged templates or typed SQL. Never concatenate values into Unsafe methods or pretend placeholders bind identifiers. Validate externally supplied date/vector/numeric values at the boundary. See the [Prisma 7 client reference](https://www.prisma.io/docs/orm/v7/reference/prisma-client-reference) and [raw-query safety](https://www.prisma.io/docs/orm/v7/prisma-client/using-raw-sql/raw-queries).

For pagination, preserve numbered-page access if required. Otherwise consider cursor-based queries with fully unique deterministic ordering and an appropriate unique cursor. Check boundary inclusion, deletion, ties, and concurrent changes against the actual generated SQL. See [Prisma 7 pagination](https://www.prisma.io/docs/orm/v7/prisma-client/queries/pagination).

For transactions, choose nested writes for dependent writes, array transactions for independent operations, and an interactive transaction when intermediate decisions need reads. Keep every participating query on the transaction client, keep external I/O outside the transaction, and test rollback on a later failure. A transaction alone does not prevent lost updates. Use atomic updates or version predicates and affected-row checks as required. Retry only identified transient conflicts, such as P2034 on version 7, with bounds and replay-safe side effects. Promise.all inside one transaction does not parallelize one connection. See [Prisma 7 transactions](https://www.prisma.io/docs/orm/v7/prisma-client/queries/transactions).

For MongoDB encountered during Prisma work, preserve the provider and the selected supported generation. Prisma 7's SQL path has no MongoDB connector. Do not port MongoDB to SQL to fix setup. Refer to the installed generation's MongoDB documentation, establish transaction/replica-set requirements, and do not use SQL Migrate commands. A requested major cutover must retain the old runnable application, compare IDs, indexes, validators, reads/writes, and restore compatibility on the same authorized copy before switching. Read [the official MongoDB upgrade guide](https://www.prisma.io/docs/guides/upgrade-prisma-orm/mongodb) for the selected release rather than retaining a static API translation catalog here.
