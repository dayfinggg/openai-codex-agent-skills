Use the manual for the connected server major. The researched baseline is PostgreSQL 18, which the official documentation marks current while 19 is a release candidate. Recheck the [version selector](https://www.postgresql.org/docs/) when used. Do not silently replace an installed older major with the baseline.

1. Establish the connection without exposing credentials. Run these PostgreSQL 18 statements through the authorized connection.

```sql
SELECT current_database(), current_user, current_schema();
SHOW server_version_num;
SHOW search_path;
```

2. Inspect only relevant schema-qualified objects. Read columns, defaults, generated expressions, nullability, keys, FK definitions and actions, checks, physical index definitions and validity, estimated sizes, comments, and dependencies. Use [information_schema](https://www.postgresql.org/docs/18/information-schema.html) and [pg_catalog](https://www.postgresql.org/docs/18/catalogs.html). Names alone do not establish joins or business meaning. For composite keys, inspect every key column in order. Exclude dropped attributes. Check partition parents/children and inherited constraints when present. PostgreSQL 18 adds NOT NULL catalog representation that older majors lack.
3. Follow relevant views, materialized views, triggers, routines, and extension ownership. Inspect routine signatures and definitions without invoking them. Check trigger enabled state and session replication role. A materialized view's definition does not establish freshness. Catalog dependencies can miss dynamic SQL and application callers. Missing objects or definitions may reflect permissions, not absence.
4. Preserve grants and RLS. Inspect policy expressions, applicable roles, owner, FORCE RLS, view security options, and current-role access before drawing access conclusions. Superusers and BYPASSRLS roles can bypass policies, and owners normally do unless forced. Policy presence does not establish active protection. Do not switch roles or disable RLS to make a query work. See [PostgreSQL 18 row security](https://www.postgresql.org/docs/18/ddl-rowsecurity.html).
5. Prefer structural metadata for exploration. Statistics such as pg_stats contain data-derived values and need task-relevant authorization just as row samples do. Do not export sensitive names, routine bodies, values, FDW option values, or user mappings unnecessarily. Sampling percentages and LIMIT cap neither pages scanned nor total work. Keep exploration read-only with a bounded statement timeout where supported. Do not run full counts, ANALYZE, refreshes, or unknown functions merely to orient yourself. A volatility label is not a safety guarantee.
6. Treat foreign tables separately. Local size and row estimates do not establish remote size, and local declarations do not prove remote constraint enforcement. Even planning can contact a remote system. Establish remote-access scope and cost before querying FDWs or definitions that invoke them.
7. Validate result semantics before tuning. Check complete join predicates, outer-join filter placement, fan-out before aggregation, COUNT(*) versus COUNT(column), NULL-sensitive NOT IN, date/time boundaries and zones, and deterministic ordering. Preserve substring versus prefix or token-search semantics. For money-like exact values preserve numeric precision. Do not change type, collation, JSON representation, or key strategy merely to impose a preferred style. CHECK alone permits NULL. Identity gaps are normal. See [PostgreSQL 18 types](https://www.postgresql.org/docs/18/datatype.html) and [constraints](https://www.postgresql.org/docs/18/ddl-constraints.html).
8. Plan the final parameterized query with plain EXPLAIN only when planning itself is authorized and vetted. EXPLAIN ANALYZE executes the statement, including write side effects. Read-only transactions and later ROLLBACK do not neutralize external function effects or all sequence effects. Use an authorized representative copy for executing uncertain queries. Bind values using the client's API, never raw string substitution. Consult the installed [psql manual](https://www.postgresql.org/docs/18/app-psql.html) before adapting placeholders to psql metacommands.
9. Read the [PostgreSQL 18 EXPLAIN procedure](https://www.postgresql.org/docs/18/using-explain.html). For measured tuning, capture EXPLAIN (ANALYZE, BUFFERS) only for an approved execution. Compare estimates with actual rows and loops, join fan-out, filter removal, sort spills, buffers, and execution time. Separate stale/selectivity estimates from missing access paths. Preserve production parameterization and data skew. An index scan is not inherently better than a sequential scan.
10. Choose indexes from the predicates, joins, ordering, and measured plan. Check existing keys and ordered prefixes first, including referencing-side FK coverage, rather than counting ORM index declarations. A B-tree candidate commonly starts with equality keys and then range/order keys, but validate the actual plan, including PostgreSQL 18 skip-scan behavior. Test collation, expression, operator class, partial-predicate implication, and covering-index visibility requirements. Use GIN, GiST, or BRIN only for suitable operators and data distribution. Weigh write, storage, and maintenance costs. Low usage counters alone do not justify dropping an index. See [PostgreSQL 18 index chapters](https://www.postgresql.org/docs/18/indexes.html) and [multicolumn indexes](https://www.postgresql.org/docs/18/indexes-multicolumn.html).

For upserts, verify the actual unique arbiter and concurrency outcome. Partial unique indexes can be inferred with a suitable conflict predicate. See [PostgreSQL 18 INSERT](https://www.postgresql.org/docs/18/sql-insert.html).
