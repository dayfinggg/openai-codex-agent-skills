1. Establish engine and exact version, migration runner and its transaction wrapping, current migration history, physical schema, table/index volume, traffic, replicas, and deployment order. Inspect affected reads, writes, background jobs, dependent views/routines, constraints, and application versions that will coexist. Separate schema DDL, data transformation, and access-policy changes.
2. Inspect generated SQL before execution. Detect rename-as-drop/add, destructive casts, constraint removal, unintended cascades, unsupported objects missing from diffs, and table rewrites. For each statement establish lock mode, duration drivers, disk/WAL requirements, transaction restrictions, and interruption state from the actual engine's documentation. Empty-table timing does not establish production safety.
3. Use an atomic change where compatibility permits. Otherwise expand the schema, deploy compatible reads/writes, backfill, validate, switch reads, and contract only after old applications and jobs are retired and the rollback window closes. Specify how old writers populate new fields throughout the backfill and cutover. Preserve old data until that condition is proven. A rename or type change can require this sequence even when DDL itself is fast.
4. Before constraints or casts, check relevant NULLs, duplicates, orphans, out-of-range and uncastable values. Validate the real conversion rather than a regex or source type name alone. Preserve uniqueness, FK actions, identity, sequences, triggers, audit/outbox behavior, grants, and RLS. Do not silently remove an invariant to make the migration pass.
5. For large backfills, use bounded batches committed independently, with durable progress and a replay-safe predicate. Advance checkpoints from actual processed keys, not arithmetic ranges or affected-row counts. Gaps and SKIP LOCKED can leave work behind, so perform a final completeness pass. Check concurrent modifications and transformation equality with NULL-safe comparison. Tune batch size/throttling to observed lock waits, latency, WAL, replica lag, and disk headroom. Resume after interruption and prove no skipped or duplicated logical work. Avoid combining a long backfill with a DDL lock-holding transaction. See [Strong Migrations backfill guidance](https://github.com/ankane/strong_migrations#backfilling-data).
6. Establish restoration before execution. Distinguish transaction rollback before commit, application rollback while schemas coexist, compensating migration, and backup restoration. Specify effects on writes made after rollout began and rehearse restoration where required. Dropping a new column loses its new data. A pre-migration fork is a rehearsal source, not a restore plan for later production writes. Preserve the last compatible application version and migration-runner bookkeeping.
7. Rehearse on an authorized representative copy or fixture, including older application reads/writes against the expanded schema and new application behavior against populated data. Exercise failure and interrupted retry where relevant. Verify values, constraints, indexes, rollback compatibility, and migration history. Do not create external copies or services outside authorization.
8. Apply only to the authorized target. Bound lock acquisition and total execution using workload-appropriate deadlines, with bounded retries and a stop condition. Restore session settings or use a dedicated migration session. Do not cancel unrelated sessions, disable constraints, or kill anti-wraparound vacuum. Afterward verify physical schema, values and invariants, application behavior, invalid indexes, waits, replication, and runner state. Stop on unexpected partial state and reconcile before retrying.

For PostgreSQL 18, read [ALTER TABLE](https://www.postgresql.org/docs/18/sql-altertable.html), [explicit locking](https://www.postgresql.org/docs/18/explicit-locking.html), and [CREATE INDEX](https://www.postgresql.org/docs/18/sql-createindex.html) before choosing these patterns.

- ALTER TABLE normally takes ACCESS EXCLUSIVE unless a subform says otherwise. Metadata-only operations still acquire locks and can queue behind long transactions. Inspect pg_stat_activity, pg_locks, and pg_blocking_pids within authorized visibility. Set lock_timeout separately from statement_timeout, which includes time waiting for locks. Choose a realistic execution deadline for long builds rather than disabling all bounds.
- A non-volatile added-column default can avoid a rewrite. now() is not a volatile default. Volatile defaults and many type conversions can rewrite the table. Check the exact subform and major rather than trusting a generic risk label.
- For CHECK or FK validation on a large table, consider ADD CONSTRAINT ... NOT VALID followed by VALIDATE CONSTRAINT. For NOT NULL, check the major's supported route, including a validated proving CHECK where appropriate. Validation still takes locks and scans. UNIQUE needs its own index-based route, not a generic NOT VALID recipe.
- CREATE INDEX CONCURRENTLY allows writes but performs additional work and waits. It cannot run inside a transaction block, and the partitioned-parent restrictions require a separate plan. Verify that the runner does not wrap it. Inspect pg_index.indisvalid and indisready after success or failure. An invalid unique index can still enforce uniqueness. Repair or remove only the task-owned failed artifact through an authorized recovery step before retrying. Attaching an existing suitable unique index as a constraint still takes a lock.

After heavy updates, check the maintenance need rather than automatically running VACUUM FULL. It rewrites the table and takes ACCESS EXCLUSIVE. DROP COLUMN, ordinary VACUUM, or table rewrite is not a claim of secure erasure across backups and replicas. See [PostgreSQL 18 vacuuming](https://www.postgresql.org/docs/18/routine-vacuuming.html).

Use [pgroll's coexistence model](https://github.com/xataio/pgroll) as an expand/contract design reference, not a requirement to install a new migration system or a guarantee of zero downtime for hand-written SQL.
