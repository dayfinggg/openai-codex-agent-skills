# Model NoSQL Data

1. Establish the required behaviors, data owner, engine and exact version or service contract, deployment topology, data sensitivity, scale, growth, latency and availability targets, consistency needs, retention, failure assumptions, and edit authority. Inspect repository instructions, manifests, existing collections or tables, key conventions, indexes, consumers, tests, capacity configuration, backup policy, and telemetry. Do not connect to or mutate a shared store without explicit authorization.
2. List concrete access patterns before modeling. For each read and write, record key or predicate, cardinality, result bound, ordering, frequency, item size, consistency, atomicity, latency, and authorization scope. Do not design from entities alone or promise ad hoc querying that the chosen store cannot support efficiently.
3. Follow project fit and file naming. Preserve the owning service or package, existing repository or model boundary, framework discovery, serialized field names, key prefixes, collection or table names, migration history, and test placement. Use local ecosystem precedent rather than importing a relational repository layout or another framework's suffixes. Treat public keys and serialized names as compatibility contracts.
4. Select the authoritative item, document, or value boundary and its lifecycle. Design primary or partition and sort keys to distribute the real workload, colocate operations that need atomicity, and keep item or document growth bounded. Account for hot keys, skew, fan-out, large values, unbounded arrays, and tenant isolation.
5. Add secondary indexes only for named access patterns. Specify projection, sparsity, uniqueness expectations, consistency, write and storage amplification, backfill behavior, and failure handling. An index does not repair a partition key that concentrates traffic.
6. Define consistency and atomicity explicitly. Choose read and write concerns, conditional writes, optimistic version checks, atomic commands, or transactions from the invariant. Bound retries, preserve idempotency, and account for stale reads, replication lag, partial batch success, conflicts, and external side effects.
7. Define retention, TTL, deletion, archival, cache invalidation, and derived-data ownership. Treat TTL as asynchronous unless the engine contract proves otherwise. Do not use a cache as the source of truth without an explicit durability and recovery contract.
8. Read only the matching engine reference: [MongoDB](references/mongodb.md), [DynamoDB](references/dynamodb.md), or [Redis](references/redis.md). For another engine, use its installed-version primary documentation and preserve this access-pattern-first workflow.
9. Protect secrets and data with least-privilege identities, server-side authorization, encryption contracts, bounded queries and values, safe logs, and resource limits. Validate dynamic keys and filters. Do not construct operator expressions from untrusted input or expose tenant identifiers and payloads through telemetry.
10. Implement the smallest complete model and consumer changes. Do not add a generic data-access layer, multi-store abstraction, dual-write path, fallback, or future index without a current consumer and verified failure contract. Hand persisted-data transitions to `migrate-databases-safely`.
11. Verify against representative size and distribution. Test positive and negative invariants, each access pattern, missing and stale data, conditional conflicts, transaction failure, retry safety, hot partitions or keys, item limits, TTL behavior, index use, latency, capacity, and recovery where applicable. Use explain or consumed-capacity evidence supported by the engine.
12. Inspect the full owned diff and remove unrelated schema cleanup or abstractions. Report observed gates and missing evidence with their consequences.

Finish when every required access pattern has a bounded, authorized, consistent, and measured storage path, with failure and capacity behavior verified for the selected NoSQL engine.
