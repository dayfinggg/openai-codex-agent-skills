First read the repository rules and recent substantive messages for the affected area through `git log --no-merges`. Preserve the established language, prefixes, capitalization, and commitlint requirements. Without local conventions, write a concise message about the concrete change in the task's language. Do not impose Git or Linux project conventions on every repository as universal requirements.

Write an imperative subject naming the action, object, and distinguishing detail. Aim for about 50 characters without sacrificing meaning. Omit a trailing period. The [Git project's contribution guidance](https://git-scm.com/docs/SubmittingPatches) treats this length as a soft limit, not a Git format restriction. An area prefix and lowercase wording after that prefix are conventions of the Git project itself.

Separate the body with a blank line. Explain the original problem, why the chosen change addresses it, and material user impact. Include limitations and tradeoffs when future maintainers need them. Do not narrate the diff, conversation history, or discarded alternatives that do not explain the final result. An obvious small change can use a subject alone. The [Linux developers' submission guide](https://www.kernel.org/doc/html/latest/process/submitting-patches.html) explains the need for context and a self-contained description.

Wrap ordinary body text at about 72 characters while keeping URLs, identifiers, and required literal content intact. [Chris Beams](https://cbea.ms/git-commit/) and [Tim Pope](https://tbaggery.com/2008/04/19/a-note-about-git-commit-messages.html) explain short subjects, blank-line separation, imperative wording, and wrapping. Their capitalization advice for an ordinary subject does not override a project's lowercase convention after a prefix.

Use [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) only when requested by the user or established by the project. Preserve the schema `type(scope): description`, with an optional scope. Use `feat` for a feature and `fix` for a bug fix. Additional types follow project policy. Mark an incompatible change with `!` or the specified `BREAKING CHANGE:` footer and describe the actual incompatibility. Do not label a documentation-only correction as an application behavior change.

Add issue references and trailers only with verified information and applicable project requirements. Do not use an issue-closing reference unless the change resolves the issue. A `Signed-off-by` trailer records the contributor's certification under project rules and is not a cryptographic commit signature. Do not add one on someone else's behalf or without a valid basis. Do not claim checks passed unless they were executed.

Before saving, compare every claim with the prospective commit. Remove vague wording, unnecessary promises, and unsupported numbers. Confirm that the subject distinguishes the change from neighboring commits and that the body explains the important reason without requiring the conversation history.
