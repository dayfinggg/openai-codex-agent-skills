# Provenance, signing, and SBOM

Provenance says where and how an artifact was built, a signature proves it was not swapped afterwards, and an SBOM lists what is inside it. Consumers need all three to decide whether to trust a release. The action SHAs below point at the release named in the comment, and need to be re-resolved before use.

## SLSA build levels

SLSA 1.2 is the current approved specification ([slsa.dev/spec/v1.2](https://slsa.dev/spec/v1.2/build-requirements)). Its Build track has three levels.

| Level | Requirement |
|---|---|
| Build L1 | The build platform generates provenance that identifies the output by cryptographic digest, and the producer distributes it |
| Build L2 | The build runs on a hosted build platform, and the provenance is signed so consumers can validate it |
| Build L3 | Provenance is strongly resistant to forgery by tenants, each build runs isolated in a fresh environment, and build steps cannot reach secrets such as the signing key |

- GitHub artifact attestations alone reach Build L2. GitHub states this in terms of SLSA v1.0.
- For Build L3, run the build in a reusable workflow, which isolates the build from the calling workflow, and verify with `--signer-workflow` pointing at that reusable workflow.
- PyPI trusted publishing does not work from inside a reusable workflow, so keep the build in the reusable workflow and the PyPI publishing job in the top-level workflow.
- SLSA 1.2 also has a Source track about branch history and review. Branch protection and review settings are repository administration, not part of a release workflow.
- NIST SP 800-204D asks that attestations are generated by a component more trusted than the build itself and that signing happens only when the build policy passes, so the attestation step comes after tests in the same trusted job.

## GitHub artifact attestations

Sources are [GitHub Docs on artifact attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations), the [how-to page](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations), and the [actions/attest README](https://github.com/actions/attest).

- **Action.** Use `actions/attest`. The older `actions/attest-build-provenance` is a wrapper around it from version 4 on, and its README says new workflows should use `actions/attest`.
- **Default predicate.** Without `sbom-path` or predicate inputs, `actions/attest` creates SLSA build provenance. With `sbom-path`, it attests a JSON SBOM in SPDX or CycloneDX format, at most 16 MB.
- **Subjects.** Files go in `subject-path`, which accepts globs. Images use `subject-name` without a tag plus `subject-digest` in `sha256:<hex>` form, and `push-to-registry: true` stores the attestation next to the image.
- **Permissions.** `id-token: write`, `attestations: write`, and `contents: read`. Images also need `packages: write` for GHCR. `artifact-metadata: write` is needed only for the storage record created with `push-to-registry`, which works for organization-owned repositories.
- **Signing.** Public repositories use the Sigstore Public Good instance with a public transparency log. Private repositories use GitHub's own Sigstore instance, which has no transparency log.
- **Scope.** Attest releases, binaries, packages, and images that consumers will verify. Do not attest frequent test builds or individual source files.
- **Limits.** GitHub states that artifact attestations are not a guarantee that an artifact is secure. They link it to its source and build, and the consumer still decides by policy.

Attesting release binaries

```yaml
  attest:
    needs: build
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write
      attestations: write
    steps:
      - uses: actions/download-artifact@9000827ccba6bdab643e8b6fd33ac0654aef8333 # v8.0.2
        with:
          name: binaries
          path: dist/
      - uses: actions/attest@1e69f48acb82d1966a394da916b4c1698aa569d6 # v4.2.2
        with:
          subject-path: "dist/*"
```

Attesting a pushed image

```yaml
      - uses: actions/attest@1e69f48acb82d1966a394da916b4c1698aa569d6 # v4.2.2
        with:
          subject-name: ghcr.io/${{ github.repository }}
          subject-digest: ${{ steps.push.outputs.digest }}
          push-to-registry: true
```

## Verifying attestations and releases

```bash
gh attestation verify dist/app-linux-amd64 -R example-org/example-app
gh attestation verify oci://ghcr.io/example-org/example-app:1.4.0 -R example-org/example-app
gh attestation verify dist/app-linux-amd64 -R example-org/example-app --predicate-type https://spdx.dev/Document/v2.3
gh release verify v1.4.0
gh release verify-asset v1.4.0 dist/app-linux-amd64
```

- `-R` or `--owner` is required. The default predicate type is `https://slsa.dev/provenance/v1`.
- `--signer-workflow` enforces which workflow signed the artifact, which matters for Build L3 with a reusable workflow.
- Verifying an `oci://` image needs a prior `docker login` to its registry.
- `gh release verify` checks that a release exists and is immutable, and `gh release verify-asset` checks a local file against the release attestation. The second cannot verify the source zip or tarball GitHub generates.
- GitHub immutable releases lock the tag to its commit and lock the assets, and they generate a release attestation automatically. Create the release as a draft, attach every asset, then publish it.

## Sigstore signing outside GitHub Actions

Source is the [Sigstore overview](https://docs.sigstore.dev/about/overview/) and the [cosign verification docs](https://docs.sigstore.dev/cosign/verifying/verify/).

- Cosign is the client. Fulcio issues a short-lived certificate bound to the CI's OIDC identity, and Rekor is the append-only transparency log, so no long-lived signing key exists to leak.
- Sign images by digest, never by tag.
- Verify against the expected identity and issuer, never by checking that any signature exists.

```bash
cosign sign "registry.example.com/app@${DIGEST}"
cosign verify "registry.example.com/app@${DIGEST}" --certificate-identity="${SIGNER_IDENTITY}" --certificate-oidc-issuer="${OIDC_ISSUER}"
```

## SBOM

- **Format.** Use the format the project or its consumers already use. CycloneDX 1.7 is published by Ecma as ECMA-424 2nd edition. SPDX 3.0.1 is the current SPDX release, while ISO/IEC 5962:2021 corresponds to SPDX 2.2.1. When nothing is set, ask the user.
- **Generation.** Generate the SBOM from the built artifact or the pushed image with a standard generator, not by hand and not from the manifest alone, so it lists what actually shipped. OWASP Top 10 2025 A03 asks to generate and manage SBOMs centrally.
- **Distribution.** Attach the SBOM to the release and attest it with `actions/attest` and `sbom-path`, so consumers can tie it to the artifact digest.

`anchore/sbom-action` runs Syft. Its `format` input accepts `spdx`, `spdx-json`, `cyclonedx`, and `cyclonedx-json`, with `spdx-json` as the default. Its `upload-artifact` and `upload-release-assets` inputs default to `true`.

```yaml
      - uses: anchore/sbom-action@66cbf4bc1f1c0d2edc94016e65bc221b6bb0ad6c # v0.24.3
        with:
          image: ghcr.io/${{ github.repository }}@${{ steps.push.outputs.digest }}
          format: cyclonedx-json
          output-file: sbom.cdx.json
      - uses: actions/attest@1e69f48acb82d1966a394da916b4c1698aa569d6 # v4.2.2
        with:
          subject-name: ghcr.io/${{ github.repository }}
          subject-digest: ${{ steps.push.outputs.digest }}
          sbom-path: sbom.cdx.json
          push-to-registry: true
```

## Build once and promote

- OWASP Top 10 2025 A03 asks for provenance, signing, and time stamping, and to promote artifacts rather than rebuild them for each environment, with immutable builds.
- NIST SP 800-204D DEPLOY-REQ-3 allows deploying only artifacts produced by the trusted build process.
- The build job outputs the digest. Every later job, whether test, scan, staging, or production, receives that digest as a job output and never runs the build again.
- Deploy jobs reference `image@sha256:<digest>` and read environment configuration at runtime.
- Before production, verify the attestation of that digest against the expected repository and signer workflow.
