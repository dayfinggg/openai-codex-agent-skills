# Design UI/UX

1. Establish the product purpose, primary users, core tasks, platform, content, brand, constraints, and measurable success. For an existing product, inspect its screens, tokens, components, assets, copy, interaction patterns, and accessibility behavior before proposing changes. Never erase a coherent local design language merely to make it look newer.
2. Gather evidence before choosing a direction. Prefer supplied references, real product content, user research, analytics, and the repository's design system. When a platform or design tool determines behavior, consult its current official guidance. Read [design standards](references/design-standards.md); use [source notes](references/sources.md) when provenance or deeper guidance matters.
3. Resolve the experience before decorating it. Define the main journey, information hierarchy, navigation, states, error recovery, responsive priorities, and content responsibilities. Remove unnecessary steps and surfaces. Do not hide missing product thinking behind cards, gradients, animation, or polished placeholder content.
4. Choose one context-specific visual direction and state it briefly through typography character, palette roles, density, layout rhythm, imagery, component geometry, and one or two signature motifs. Distinctiveness must support the product's meaning. Favor familiarity for controls and navigation; spend originality on composition, brand expression, imagery, and memorable moments.
5. Build from a small system: semantic color, typography roles, spacing scale, grid or container rules, radii, borders, elevation, icon treatment, motion, and reusable component variants. Reuse the existing system when one exists. Encode repeated decisions as tokens or shared primitives rather than one-off values.
6. Reject generic AI defaults unless the context genuinely calls for them: purple-on-white gradients, gratuitous glass, glow, oversized rounded cards, pill-shaped everything, repetitive bento grids, identical section stacks, decorative dashboards, random icons, fake metrics, generic hero copy, excessive empty space, or motion on every element. Do not replace one cliché with arbitrary eccentricity. Edit toward fewer, stronger choices.
7. Make hierarchy immediately legible. Give each view one primary task or focal point; let supporting chrome recede; group by proximity and alignment; use whitespace to express relationships; keep information-dense products compact enough to scan. Preserve tables, lists, canvases, timelines, or full-bleed compositions when they fit better than cards.
8. Treat content as interface material. Use specific, concise, user-facing language and real domain terminology. Labels must predict outcomes; errors must explain recovery; empty, loading, success, disabled, selected, hover, focus, and destructive states must be designed. Do not invent testimonials, business claims, metrics, or product capabilities.
9. Meet WCAG 2.2 AA for web work and the applicable platform accessibility guidance. Use semantic structure, native controls where possible, complete keyboard operation, visible focus, logical reading and focus order, accessible names, sufficient contrast, non-color status cues, adequate targets, zoom and text resizing, reflow, reduced-motion support, and assistive-technology announcements. Account for localization, longer text, RTL layouts, touch, pointer, and keyboard input.
10. Use motion only to explain causality, continuity, hierarchy, or status. Prefer short, interruptible transitions; avoid blocking input, cumulative delays, scroll hijacking, and decorative loops. Respect `prefers-reduced-motion` and platform settings. Match implementation complexity to the chosen direction: restraint requires precision, not absence of craft.
11. Implement native, responsive, production-quality UI in the project's established stack. Preserve working behavior and existing accessibility. Use real components and code-native text and controls; never ship a screenshot as the interface. Coordinate with `$production-code-quality` for retained source code and `$design-project-architecture` when component ownership or frontend boundaries materially change.
12. Validate in the rendered product, not only in source. Exercise the main journey and all material states with keyboard and pointer; inspect narrow, standard, and wide viewports; light and dark themes when supported; 200% text sizing and 400% page zoom or equivalent narrow reflow; reduced motion; overflow; long and localized copy; loading; empty; error; and slow-content behavior. Compare screenshots with the intended direction, correct visible drift, and repeat until the result feels coherent at both page and component scale.

Finish only when the interface is useful, distinctive for a defensible reason, internally consistent, accessible, responsive, and visually verified. Report material trade-offs, untested states, and any departure from the established design system.
