Use when creating or redesigning interfaces, screens, flows, components, design systems, responsive behavior, accessibility, public-web content structure or SEO-aware presentation, or when polishing an existing UI. Preserve product and platform constraints and reject generic AI-generated aesthetics. Skip backend-only changes and frontend work with no visual, content, interaction, or discoverability impact.

# Design UI/UX

1. Establish the product purpose, primary users, core task, platform, content, brand, constraints, and measurable success. For an existing product, inspect its rendered screens, tokens, components, assets, copy, states, interactions, and accessibility before proposing changes. Preserve a coherent local design language unless the task explicitly requires replacing it.
2. Gather evidence before choosing a direction. Prefer supplied references, real content, user research, analytics, the repository's design system, and current platform guidance. Separate observed facts from assumptions. If an unresolved assumption can change information architecture, navigation, a form, or a critical flow, name it and choose the smallest realistic way to test it. Read [design standards](references/design-standards.md), and use [scenario examples](references/scenario-examples.md) when the surface or complexity needs a concrete pattern. Use [source notes](references/sources.md) for provenance or deeper guidance.
3. Scale the process to the work. For a simple view, define one primary task, its main action, representative content, and material feedback states. For multi-screen, form-heavy, data-dense, collaborative, role-based, or safety-critical work, define information architecture, journeys, states and events, roles and permissions, data responsibilities, and recovery before visual refinement. Never substitute polished static screens for a working flow.
4. Resolve the experience before decorating it. Define navigation, reading and focus order, hierarchy, decision points, state transitions, error recovery, responsive priorities, and content responsibilities. Remove unnecessary steps and surfaces. Build forms as a short conversation toward the user's goal: request only data needed for the next outcome, use the user's language, and explain unexpected requirements before input.
5. State one context-specific visual direction through typography character, palette roles, density, spatial rhythm, imagery, geometry, and one or two signature details. Check whether the same direction could describe any similar product; if so, make it more specific. Favor familiar controls and navigation. Spend originality on composition, brand expression, imagery, and memorable moments that do not make the product harder to use.
6. Build from a small system of semantic color, typography roles, spacing, grid or container rules, radii, borders, elevation, icons, motion, and reusable variants. Reuse existing tokens and components first. For new systems, separate primitive, semantic, and component decisions only when each layer has a current use. Avoid one-off values and speculative component libraries.
7. Make hierarchy immediately legible. Give each view one primary task or focal point, let supporting chrome recede, and group by proximity and alignment. Use headings for real content structure, not as decoration or a substitute for spacing. Preserve relative hierarchy when text grows. Avoid tiny or light essential text, arbitrary type sizes, excessive typefaces, centered long copy, and several equally loud calls to action.
8. Choose containers by meaning. Use a card only for a self-contained comparable object or a clear interaction boundary. Keep repeated items consistent in identity, decision-critical attributes, metadata, and action placement. Prefer plain sections, lists, tables, feeds, timelines, canvases, or full-bleed composition when they express the task better. Do not turn every region into a rounded floating card or every fact into a badge.
9. Reject generic AI defaults unless the brief genuinely supports them: purple-on-white gradients, gratuitous glass or glow, oversized rounded cards, pill-shaped everything, repetitive bento grids, identical section stacks, decorative dashboards, random icons, fake metrics, generic hero copy, excessive empty space, or motion on every element. Do not replace one cliché with arbitrary eccentricity. Edit toward fewer, stronger choices.
10. Treat content as interface material. Use specific, concise, user-facing language and stable domain terms. Make labels predict outcomes and errors explain recovery. Design empty, loading, success, disabled, selected, hover, focus, offline, permission, and destructive states when applicable. Do not invent testimonials, claims, metrics, capabilities, or data. Distinguish a mockup, prototype, and production interface accurately.
11. Apply SEO only to public pages intended for search discovery. Preserve a unique descriptive document title, a clear main topic, meaningful heading structure, visible text in the rendered DOM, semantic HTML, stable URLs, and crawlable links. Add canonical URLs, metadata, structured data, sitemaps, or index controls only when the content model requires them. Never use keyword stuffing, search-only copy, misleading headings, or SEO rules on private product screens without a product need.
12. Meet WCAG 2.2 AA for web work and the applicable platform accessibility guidance. Prefer semantic structure and native controls. Provide complete keyboard operation, visible unobscured focus, logical reading and focus order, accessible names, sufficient contrast, non-color status cues, adequate targets, zoom and text resizing, reflow, reduced-motion support, and assistive-technology announcements. Account for localization, longer text, RTL layouts, touch, pointer, keyboard, and platform text-size settings.
13. Use motion only to explain causality, continuity, hierarchy, or status. Keep it brief, interruptible, and responsive. Avoid blocked input, chained delays, scroll hijacking, decorative loops, and layout instability. Respect `prefers-reduced-motion` and platform settings. Reserve space for late content and media, and design loading so it does not shift the interface unexpectedly.
14. Implement native, responsive, production-quality UI in the established stack. Preserve working behavior and accessibility. Use real components, code-native text, semantic controls, and representative data. Never ship a screenshot as the interface or accept generated visuals as proof of behavior. Prefer structured design files, tokens, component mappings, and targeted annotations to repeated whole-screen regeneration. Coordinate with `$production-code-quality` for retained source code and `$design-project-architecture` when ownership or frontend boundaries materially change.
15. Validate the rendered product, not only the source. Exercise the main journey and every claimed interaction with keyboard, pointer, and touch where applicable. Inspect narrow, standard, and wide viewports, supported themes, 200% text sizing, 400% page zoom or equivalent narrow reflow, reduced motion, overflow, long and localized copy, loading, empty, error, permission, and slow-content behavior. For public indexable pages, verify rendered search-visible content and links. When performance is in scope, measure rather than infer and use current Core Web Vitals guidance. Compare screenshots with the chosen direction and correct visible drift.

Finish only when the interface is useful, context-specific, internally consistent, accessible, responsive, and visually verified. Report material trade-offs, evidence, untested states, and any departure from the established design system without promotional language.
