# Simplify Code

Apply this bounded workflow as SCC-Guard for explicit simplification. Use `production-code-quality` alongside it when changing retained production code. This skill owns the simplification decision, while the production skill owns language and platform gates.

1. Confirm the explicit simplification goal, owned surface, observable behavior to preserve, and permitted change boundary. Use `diagnose-root-cause` first when the cause is unknown. Use `design-project-architecture` when module, data, runtime, deployment, or team-ownership boundaries are the decision. Do not invoke this workflow for ordinary implementation.
2. Establish a characterization baseline before editing. Run the narrowest existing behavior, contract, and error-path checks that cover the target. Record public callers, current output, failures, and any relevant performance measurement. Separate pre-existing failures from candidate regressions.
3. Build a compact responsibility and complexity map for the target. Identify its responsibility and owner, callers and consumers, public or persisted contracts, state and resource lifetime, control-flow or duplication hotspot, and configured quality gates. Keep the map proportional. One line per applicable item is enough for a local change. Read [code-shape thresholds](references/code-shape-thresholds.md) only when a configured gate fires or code shape is offered as the reason to refactor.
4. Compare the same three positions against current evidence: leave the code as-is, use a local extraction or deletion, and use at most one viable alternative. Assess behavior preservation, cohesion, diff surface, new concepts, compatibility, verification, and measured performance. Discard a position that cannot meet the current requirement. Choose the simplest fully sufficient position and do not expand this into a design ceremony when the evidence makes one position plainly sufficient.
5. Track the complexity vector separately: `C = {production LOC, touched owners, public surface, abstractions, dependencies, configuration, state or concurrency, branch complexity, duplication}`. The default budget is zero for a new production dependency, public contract, abstraction, configuration key, stateful component, concurrency mechanism, unrelated owner, future hook, independent cleanup, or weakened test. Exceed a coordinate only for a current consumer or contract after proving simpler existing mechanisms insufficient.
6. Implement deletion-first. Remove dead paths, wrappers, flags, options, duplicate representations, and dependencies before extracting a new unit. Then prefer the existing local path, a language feature, the standard library, an installed dependency, and a small local helper in that order. Do not add a generic API, interface, registry, mode, fallback, extension point, framework, or future configuration without a current verified consumer.
7. Follow the closest repository instructions, package root, configured generator, formatter, analyzer, compiler, and neighboring naming and layout precedent. Preserve mechanically significant route, import, migration, generated, serialized, and public names. Do not create, move, split, or rename a file solely to impose another ecosystem's convention or satisfy an unconfigured count.
8. Preserve applicable signatures, types, errors, defaults, ordering, side effects, CLI output and exit codes, configuration precedence, schemas, wire and persisted data, lifecycle, cancellation, concurrency, and performance guarantees. Verify changed callers and consumer contracts. If compatibility cannot be preserved, stop treating the work as a bounded simplification and obtain explicit authority plus migration and rollback requirements.
9. Measure performance only when the target is a hot path, a performance contract can change, or the user requested it. Compare correct baseline and candidate behavior under the same recorded environment and representative workload with repeated measurements and variation. Check traded resources. Do not claim an improvement when the effect is noise or when work was skipped.
10. Run narrow checks, then broaden according to the changed risk. Use an independent discriminator where consequence warrants it, such as a pre-change failure, known bad mutant, property, differential check, old-to-new round trip, downstream build, or hidden composed case. Never weaken an assertion, change an oracle, skip a test, or hard-code a fixture to make the refactor pass.
11. Inspect status, diff statistics, whitespace, and every changed line in context. Assign each hunk to the simplification goal, a necessary test, contract preservation, migration, or required retained documentation. Delete every untraceable hunk and unused concept, then repeat affected checks. Preserve the baseline revision or hashes and an exact rollback operation. Verify rollback when external state or migration makes source reversion insufficient.

Use [sources](references/sources.md) only when a primary reference is needed to justify a disputed trade-off.

Finish when the bounded code is simpler on the applicable responsibility or complexity dimensions, every preserved contract has proportionate evidence, the complete diff contains no speculative or unrelated change, performance claims are measured, and rollback remains usable.
