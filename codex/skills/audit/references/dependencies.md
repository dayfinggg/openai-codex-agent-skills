1. Build the inventory without executing target code. Reject unreadable, malformed, or incorrectly encoded manifests and lockfiles rather than silently producing an empty inventory. Record ecosystem, canonical package identity, source registry or repository, exact version, lockfile path or build-list evidence, direct/transitive status, and runtime/build/test scope. Count distinct identity-version-source tuples. Never replace an unresolved range with the registry's latest release and call it the installed version.

   - For npm, inspect package-lock.json or npm-shrinkwrap.json, including workspace links, aliases, resolved URLs, integrity, overrides, optional and development dependencies. For yarn.lock or pnpm-lock.yaml, use the parser belonging to the observed format version or label unresolved entries. Read package.json to identify direct dependencies.
   - For Python, inspect uv.lock, poetry.lock, pylock.toml, or fully pinned requirements as applicable. Respect extras, environment markers, platform wheels, index mappings, editable paths, and VCS commits. A universal lock can contain alternatives that the selected environment never installs. A manifest pin proves a declaration, not the complete transitive environment.
   - For Go, inspect go.mod, go.work, replace/exclude directives, vendoring, and toolchain version. go.sum contains checksums, not a selected-version lock. Where graph loading is authorized, use `go list -m -json all` from the module directory in a disposable copy with the same workspace and configuration. Record replacement identities and selection failures. Without a build list, label go.mod requirements as minimums, not resolved versions. See the [Go Modules Reference](https://go.dev/ref/mod#minimal-version-selection).

2. Verify that the package and version exist at the actual source. Do not attribute a public namesake's advisories or publisher information to a private, workspace, local, vendored, or VCS dependency. Resolve those to their own source or mark the criterion unavailable. Confirm registry spelling and namespace, repository ownership, and the official project's link back to the package before suggesting any replacement.

3. Check known advisories for every resolved tuple, including transitives. Use the project's configured service where appropriate. Account for data sent to that service, especially private names. Read installed CLI help and version-matched documentation before running a command. Preserve JSON, stderr, and exit status without masking failures.

   Commands below are documented for npm 11/12, pip-audit 2.10.1, and govulncheck 1.x. Substitute actual paths in the selected shell. Run from the target project or its disposable copy, never from the skill directory.

   - `npm audit --json --package-lock-only --ignore-scripts` queries known vulnerabilities without applying fixes. Inspect omitted dependency types and workspaces. An audit threshold changes the exit condition, not the report contents. Do not run `npm audit fix`. See [npm audit 12](https://docs.npmjs.com/cli/v12/commands/npm-audit/) and [npm audit 11](https://docs.npmjs.com/cli/v11/commands/npm-audit/).
   - `pip-audit --no-deps --disable-pip -r resolved-requirements.txt -f json` accepts a complete exact-pin inventory without pip resolution. Include the already-resolved transitives and selected markers. Do not feed arbitrary requirements or project metadata into a resolver merely to audit them. pip-audit's [security model](https://github.com/pypa/pip-audit/tree/v2.10.1#security-model) warns that resolution can execute code. It detects known vulnerabilities, not arbitrary malware. Never use `--fix` during inspection.
   - `govulncheck ./...` provides source-call analysis only when that analysis is requested. Record Go version, platform, tags, and test inclusion. Do not present a metadata-only module advisory sweep as equivalent reachability analysis. Existing binaries can be analyzed with `govulncheck -mode binary path/to/binary` without running them. See [govulncheck](https://pkg.go.dev/golang.org/x/vuln/cmd/govulncheck).

4. For metadata-only checking, submit exact ecosystem-name-version tuples to [OSV querybatch](https://google.github.io/osv.dev/post-v1-querybatch/). Reconcile positional responses with requests, follow each query's pagination token, then retrieve complete records for returned IDs. Inspect affected ranges, aliases, withdrawn records, fixes, and modification dates. Deduplicate CVE/GHSA/OSV aliases without losing affected package versions. Check [GitHub Advisory Database](https://github.com/github/advisory-database) review status and upstream disclosures when records disagree. OSV and GitHub can share upstream data and are not necessarily independent confirmations. Report unresolved discrepancies rather than selecting the most alarming value.

5. Collect maintenance and takeover indicators for direct dependencies, expanding to suspicious transitives when useful.

   - Read registry deprecation, PyPI per-file yanking and reason, Go retractions, archived status, dated releases, substantive repository activity, security policy, and maintenance announcements. Old release dates alone do not prove abandonment. A yank or retraction needs its stated reason.
   - Measure current npm publish rights separately from historical release metadata and repository contributors. Do not infer publisher counts for ecosystems that do not expose them. Downloads require the registry's measured period and source. PyPI JSON's deprecated downloads field is not a measurement.
   - Inspect lifecycle scripts, newly introduced publishers, name similarity, namespace/source changes, unexpected network endpoints, credential access, obfuscation, and release-to-source differences. Scripts and minification are indicators requiring context. For a malware finding, connect the observed entry point, sensitive data or behavior, and destination with exact artifact evidence. Do not label a package malicious from one suspicious API name.
   - Read individual [Scorecard checks](https://github.com/ossf/scorecard/blob/main/docs/checks.md), their date, repository commit, and supporting details. Investigate Dangerous-Workflow and Binary-Artifacts findings. Treat Token-Permissions, Code-Review, aggregate score, download volume, provenance presence, and security-policy presence as context unless a concrete exposure is established. Do not use a blanket score threshold as a takeover verdict.

6. For every criterion, retain its supporting datum or unavailability reason. Reconcile assessed and unavailable counts against the full inventory. Distinguish a confirmed missing public resource from authentication, rate-limit, timeout, or network failures. Registry absence plus an empty advisory response cannot establish safety.

7. Verify that a proposed fixed or replacement version exists and addresses the applicable advisory. Name compatibility cost, including major-version changes. Assess whether suppressing install scripts is viable from the project's build requirements without installing or building during a metadata audit. Do not change dependencies or claim the build works. License compliance and unsupported ecosystems remain outside this procedure.

The [OpenSSF evaluation guide](https://best.openssf.org/Concise-Guide-for-Evaluating-Open-Source-Software) supplies identity and sustainability checks. The [PyPI JSON API](https://docs.pypi.org/api/json/) documents version-specific release metadata. Use [npm view](https://docs.npmjs.com/cli/v12/commands/npm-view/) for explicit version metadata and current packument fields without installing the package.
