1. Resolve the project directory, project name, compose files, overrides, profiles and environment sources actually used by the caller. Prefer compose.yaml for new setups, but preserve supported legacy filenames. Development overrides may load automatically, so select production files explicitly and exclude source/debug overrides from production.
2. Keep service names stable and use service DNS names and container ports for inter-service connections. Prefer the default project network unless isolation is needed. Declare named volumes and custom networks, and preserve externally owned resources. Avoid container_name unless an existing external caller needs it. Use the existing restart policy or an appropriate bounded recovery policy for long-running services.
3. Give database, cache and broker dependencies native readiness checks with interval, timeout, retries and start_period matched to startup behavior. Verify the command exists in the image and handles authentication without leaking credentials. Use `service_healthy` where readiness is required and `service_completed_successfully` for a required one-shot task. `service_started` only orders startup. Keep the dependency graph acyclic. Application retry/reconnect behavior is still needed after startup or dependency failures.
4. For scratch or distroless images use an application-native check or the existing external readiness probe. A health sidecar must remain running, probe the correct endpoint and be the dependency actually awaited if it supplies Compose health. Do not silently treat sidecar health as the application's own container health or install a shell solely to satisfy an unsuitable probe.
5. Use declared named volumes for new persistent data unless the required platform storage contract says otherwise. Source bind mounts belong in development settings, not production. Preserve intentional existing bind mounts after checking paths, permissions and host-platform behavior. Use read-only mounts for immutable inputs and tmpfs for disposable scratch data. Avoid anonymous volumes where ownership cannot be tracked. Prevent source sync from replacing container-built dependencies with host dependencies.
6. Keep unauthenticated datastores off host ports. Publish local-development application ports and any datastore ports needed by host tools on loopback by default. Broader access must follow the requested network contract. Do not mount the Docker socket or add host networking as a troubleshooting shortcut.
7. Use versioned images, with digests where immutable releases require them. Never hardcode real credentials in Compose or connection URLs. Supply runtime secrets through the established secret mechanism or an untracked env_file for local development. Protect secret files in both .gitignore and .dockerignore. Clearly mark any development-only credential fallback. Build secrets and runtime secrets are separate grants.
8. Keep source sync, debug ports and verbose settings in development overrides. Use bind mounts or supported Compose Watch actions according to the existing workflow. Verify plugin support before introducing watch features. Do not require a development convenience or rename working files during an unrelated service fix.
9. From the project directory run `docker compose config --quiet` with the caller's exact file, profile, project and environment arguments. It validates without dumping the resolved model but still reads env files, and diagnostics can expose sensitive data. Inspect source files for secrets, image versions, volumes, network exposure, health checks and dependency conditions. If resolved inspection is necessary use dummy credentials in a disposable copy.
10. When authorized, build and start only the intended project and services using that same configuration. Inspect `docker compose ps`, health state and bounded startup logs. Test DNS and the actual database/protocol connection from the application network, not only ping. Verify readiness, reconnect behavior where changed, and persistence across authorized container recreation. A running state is not a health result. For a new setup, confirm the documented command path builds and starts the intended stack.
11. Preserve data during cleanup. `docker compose down` does not remove named volumes, but still stops the stack and needs authorization. `down -v` removes managed named volumes and attached anonymous volumes, not external volumes. `rm -v` removes attached anonymous volumes. Never use either volume-deleting form as routine smoke-test cleanup. Identify standalone and external volume ownership before any separately authorized removal.

Check [the Compose model](https://docs.docker.com/compose/intro/compose-application-model/), [startup and shutdown ordering](https://docs.docker.com/compose/how-tos/startup-order/) and [config validation](https://docs.docker.com/reference/cli/docker/compose/config/) for the installed plugin.
