1. Read the application's actual build and start commands, lockfiles, native dependencies, ports, writable paths and deployment platform. For a new setup create `.dockerignore` at each build context root before the first build, then the Dockerfile. Add Compose when the requested local stack needs it. Prefer containerized development dependencies to host-level database or cache installs. Keep one Dockerfile with named development and runtime stages when practical, and preserve existing layouts.
2. Exclude VCS data, editor files, host dependencies rebuilt in the image, caches, test outputs and credentials from the context. Include nested credential files such as `**/.npmrc`, `.env` variants, package registry settings, cloud credentials, SSH/TLS keys and kubeconfig. Keep source, lockfiles, licenses and other inputs the actual build requires. `.dockerignore` is defense in depth and cannot make credential-copying safe.
3. Select a trusted, maintained base compatible with the installed language and native ABI. Use an explicit version and an immutable digest for reproducible production artifacts. Plan deliberate digest updates with rebuilds, tests and vulnerability review. Choose slim, hardened, distroless or scratch only when libraries, certificates, timezone data and executable requirements permit. Do not force Alpine or disable cgo merely to reduce size.
4. Separate compilation and development dependencies from runtime using named stages. Copy only required artifacts and runtime dependencies. For Node distinguish build dependencies from production dependencies or standalone output. For Python match interpreter, ABI and virtual-environment path across stages. For Go verify static linking before scratch. For Java keep the JDK in the build stage and a compatible runtime in the final stage. Preserve test execution elsewhere if a packaging stage omits tests.
5. Put stable dependency manifests and lockfile installation before changing source. Use lockfile-respecting package-manager commands. Bind mounts in a build step are read-only by default and their writes do not persist. Use COPY instead when the command must update a manifest or retain mounted files. A Go dependency command may need to update go.mod or go.sum, so do not assume read-only binding always works.
6. Use BuildKit cache mounts at the package manager's real cache path, matching its user UID/GID. Apt cache mounts need `sharing=locked`. Keep update and install together, install only required packages and keep package caches outside final layers. When not using mounts, remove package lists in the installation layer. Source-only edits should reuse dependency installation, while lockfile edits must invalidate it. Network content and secret-value changes alone do not guarantee cache invalidation. Use deliberate invalidation when credential or remote-input changes require rerunning a step.
7. Use the supported Dockerfile frontend, commonly `# syntax=docker/dockerfile:1`. Use COPY for local files. Consider COPY --link for independent artifact layers only when destination symlinks and prior directory state are not required. Verify ownership resolution and prefer explicit numeric IDs when appropriate. Keep WORKDIR explicit, document listening ports with EXPOSE, set source/revision labels when available and use exec-form startup for signal delivery.
8. Run the application as a dedicated non-root user with the required file ownership. Review effective runtime UID, writable directories, CPU/memory limits, capabilities, read-only mounts and filesystem, no-new-privileges and existing seccomp/AppArmor/SELinux protections. Apply compatible hardening within scope and exercise it. Do not add privileged mode, expose the daemon socket, disable host protections or change daemon ownership to make a test pass.
9. Pass build credentials through BuildKit secret or SSH mounts, never ARG, ENV, COPY or ADD. Prevent dependency scripts and RUN commands from writing secrets into layers, caches or logs. Private-only installs should fail when the required secret is absent, while public installs should not require a dummy secret. Use least-privilege registry tokens. Review every forwarded SSH identity with `ssh-add -l`, use a task-specific agent without changing the user's agent, and preserve host-key checking with independently verified known_hosts. Direct SSH key-file forwarding does not support passphrase-protected keys.
10. From the actual context directory, build the requested target and platform. For an authorized single-platform local test, use `docker buildx build --load -t <task-image> .`, adapting Dockerfile and context arguments to the project. Loading is necessary before local inspection with builders that do not automatically export images. Do not push as a build test.
11. Inspect the built image's size, layer sizes, configured user, WorkingDir, ExposedPorts, Entrypoint and Cmd with image inspection and history. Verify the effective non-root user through a supported runtime check, without assuming whoami or a shell exists. Review source and intermediate-stage credential handling before building. Final image history alone cannot reveal files left only in intermediate caches, and regex matches alone cannot prove a leak or its absence. Scan the built artifact with the existing vulnerability/secret tooling and inspect findings against policy.
12. Exercise application startup, its listening address and port, dependency connectivity, the changed user path and graceful termination. For caching work compare a repeat build, a source-only change and a dependency-input change in a disposable context. Compare size and layers against the project's measured baseline, not universal language-size or layer-count thresholds. Keep logs secret-free, especially when using plain progress output. Remove only task-owned disposable resources after no process needs them.
