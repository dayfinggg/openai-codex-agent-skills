1. Establish the exact authorized application and environment, tested revision or digest, deployment mechanism, configuration source, runtime versions and acceptance path. Reuse established authentication without displaying values. Verification alone permits inspection and checks, not starting a new release.
2. Trace source, tested build and deployed runtime identity. Promote the tested immutable artifact instead of rebuilding an untracked variant. Record configuration identity without secrets. Confirm platform architecture and dependent service versions. Resolve every target from the release configuration, not a similarly named reachable server.
3. Before rollout identify old/new application, schema, cache, worker and protocol compatibility during coexistence. For migrations review lock duration, backfill completion, single-run coordination, data preservation and recovery evidence. Use additive expansion before switching readers/writers and defer destructive contraction until old consumers are gone. Do not run down-migrations automatically with a code rollback. If compatibility cannot be established, block the dependent rollout and complete independent checks.
4. Establish a supported restoration path before mutation. Preserve the previous artifact, required configuration and revision history. Distinguish application rollback from schema restoration and backup recovery, including writes lost during recovery. Verify backup availability and restore evidence when data recovery is part of the plan. A rollback plan is not a successful rollback rehearsal.
5. Use the existing rollout strategy. For rolling or blue-green changes verify spare capacity, readiness-gated traffic admission, graceful drain and shutdown, connection/session handling and worker ownership. If the platform cannot overlap healthy instances, do not promise zero downtime. Compose startup ordering alone does not provide a zero-downtime rollout.
6. Separate liveness, readiness and a user-visible acceptance check. Use the release's actual startup budget, observation window and failure thresholds. Avoid treating a generic health endpoint as proof that the changed operation, database access or queue consumption works.
7. Execute only the authorized release through the existing system. Coordinate migrations and background backfills with the version transition. Refresh FPM/OPcache, long-lived workers and caches only when the application requires it. Do not introduce a new platform, approval gate or unrelated infrastructure change.
8. Verify runtime artifact identity, effective non-secret configuration, traffic readiness, the changed user path and a relevant failure path. Inspect bounded logs, errors, latency and dependent jobs for the observation window. On acceptance failure stop further promotion and use the authorized restoration procedure. Verify identity and acceptance again after restoration. If restoration needs ungranted data loss or another decision, stop that mutation and report the exact choice required.
9. Remove only task-owned disposable release files and resources after no running process requires them. Report the actual revision/digest, environment and observed acceptance or restoration result. Explicitly identify checks that could not run, rather than labeling the deployment ready.

Use [Kubernetes rollout and rollback guidance](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/) only for Kubernetes targets. Use [GitLab's zero-downtime procedure](https://docs.gitlab.com/update/zero_downtime/) for its concrete examples of staged migrations and draining, not as commands for unrelated systems.
