Review the behavior generated by the ORM, not only the source-level query.

1. Identify the ORM and driver versions, database provider, mapping, unit-of-work lifetime, and changed callers. Read the actual query or operation and its consumers.
2. Determine result grain, required ordering, cardinality, and mutation contract. Inspect deferred execution and points of materialization. Do not infer bounded memory from an iterator-shaped API.
3. Observe generated SQL and round trips through existing logging or a representative test. Check N+1, repeated saves, duplicated joined rows, oversized includes, and hidden lazy loading.
4. Verify pagination under the intended ordering and concurrent changes. Ensure selection and counts represent the same domain filter. Offset or cursor pagination must fit the actual contract.
5. Trace transactions, change tracking, optimistic concurrency, and immediate bulk operations. Check whether an update bypasses tracked state, events, validators, or audit/outbox behavior.
6. Prefer a focused projection, loading strategy, or batch change that preserves semantics. Do not fix N+1 by globally eager-loading every relation or suppressing the failing path.
7. Verify result identity, query count, transaction behavior, and resource disposal. For performance claims, use equivalent data and parameters and include database work rather than only client stopwatch time.

For EF Core, read the [EF Core procedure](../ef-core/guide.md). For Prisma, use the installed prisma skill and its version-matched procedure. Consult the selected ORM's official query, transaction, and loading documentation before choosing its APIs. Ordinary review does not authorize a new repository layer or database-access policy.
