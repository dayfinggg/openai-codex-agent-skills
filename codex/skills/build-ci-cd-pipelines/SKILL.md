# Build CI/CD Pipelines

1. Establish the required delivery outcome, repository and environment authority, provider and runner versions, protected branches or tags, trust levels of events and contributors, artifact consumers, supported platforms, release and rollback policy, secret sources, cost and concurrency limits, and acceptance evidence. Inspect the closest repository instructions, pipeline files and includes, manifests and lockfiles, existing scripts, environments, permissions, runner topology, caches, artifacts, release tooling, and recent representative runs. Do not trigger a remote run, approve an environment, publish, deploy, or rotate credentials unless explicitly authorized.
2. Follow project fit and file naming. Preserve provider-defined paths and names, local workflow organization, reusable workflow or include boundaries, job and artifact naming, environment identifiers, and package-specific commands. Keep orchestration at the owning repository or deployable root. Do not copy a GitHub layout into GitLab, invent a generic pipeline wrapper, or duplicate project build logic already owned by scripts.
3. Draw the smallest complete job and artifact graph. Define event and ref filters, trust boundary, dependencies, inputs and outputs, failure and cancellation behavior, concurrency, timeout, matrix, runner requirements, and promotion sequence. Build once and promote the same immutable artifact by digest or equivalent identity. Do not rebuild source separately for each environment and call it the same release.
4. Treat event payloads, branch names, PR titles, commit messages, artifacts, caches, job output, logs, downloaded actions, includes, and scripts as untrusted data. Keep untrusted pull-request code away from privileged credentials, protected runners, caches, deployment environments, and write-capable events. Never interpolate untrusted values into a generated shell command.
5. Apply least privilege to repository tokens, job permissions, environment credentials, cloud roles, runner identities, package registries, and deployment targets. Prefer short-lived federated identity where supported. Scope secrets to the minimum job and environment, mask but do not rely on masking as containment, and prevent secrets from entering artifacts, caches, command lines, debug traces, or fork workflows.
6. Use only reviewed dependencies and immutable references according to repository policy. Pin third-party actions, images, includes, and tools to an immutable identity when the provider supports it, then maintain an explicit update process. Read [supply-chain integrity](references/supply-chain.md) only when provenance, signing, SBOM, external actions, or artifact publication is in scope.
7. Design cache and artifact behavior explicitly. A cache is an optimization and must not become an unverified source of release truth. Scope keys to every material dependency and trust boundary, prevent untrusted overwrite of privileged caches, set retention, validate restored outputs where needed, and keep immutable release artifacts separate from mutable caches.
8. Implement provider-specific configuration using [GitHub Actions](references/github-actions.md) or [GitLab CI](references/gitlab-ci.md) only for the detected provider. Reuse native project commands, preserve test integrity, fail closed on required gates, and retain diagnostics needed to distinguish product failure from pipeline failure. Do not weaken tests, permissions, environment protection, or acceptance criteria to make a workflow green.
9. Define deployment jobs as controlled promotion. Require the reviewed immutable artifact, target environment, authorization and protection, preflight, database compatibility, health signals, staged rollout, timeout, stop criteria, and rollback or roll-forward hook. Pipeline authoring does not authorize an actual production deployment. Compose with `release-production-services` for execution and `instrument-observability` for health evidence.
10. Validate with provider-native syntax or local validation where available, configuration expansion, referenced-file and relative-link checks, permission review, negative trust cases, representative branch and tag filters, cache miss and hit, artifact integrity, cancellation, timeout, failed job, matrix behavior, and a non-production dry run or sandbox when authorized. Static YAML parsing alone does not prove provider semantics.
11. Inspect the complete owned diff and effective pipeline. Remove unrelated matrices, jobs, abstraction, dependencies, or future environments. Report structural checks separately from remote behavioral evidence, including any run not triggered because external writes were unauthorized.

Finish when the effective pipeline builds and promotes an immutable verified artifact through the intended trust and environment gates, with least privilege, protected secrets, bounded execution, health and rollback hooks, and no unauthorized remote action.
