# Instrument Observability

1. Establish the decision or user outcome the telemetry must support, edit authority, system and data boundaries, runtime and telemetry-stack versions, existing service identity and conventions, reliability targets, retention and cost constraints, deployment topology, and acceptance evidence. Inspect the closest repository instructions, manifests, existing instrumentation, collectors or agents, semantic conventions, dashboards, alerts, runbooks, sampling, exporters, and representative signal output. Do not send new telemetry to an external backend without explicit authorization.
2. Follow project fit and file naming. Preserve the established instrumentation library and initialization boundary, service and environment resource attributes, metric namespace, logger structure, dashboard and alert locations, configuration source, and generated-versus-retained artifacts. Keep telemetry near the owning component where repository precedent does so. Do not introduce a second observability stack or generic wrapper without a current interoperability need.
3. Define the observable contract before adding signals. Name the actors, critical operations, failure modes, decisions, SLI or diagnostic questions, dimensions needed to answer them, expected volume, freshness, and owner. Prefer the smallest signal set that closes those questions. Do not emit data merely because it is available.
4. Read [OpenTelemetry](references/opentelemetry.md) only when traces, context propagation, OTel metrics or logs, exporters, collectors, or semantic conventions are involved. Preserve trace context across supported process and network boundaries, record errors without duplicating high-volume events, and use exact-version stable conventions where available.
5. Design logs as structured events with stable fields, severity, event identity, operation and correlation context, and bounded payload. Keep secrets, credentials, tokens, raw bodies, personal data, and high-risk identifiers out of logs. Sanitize untrusted text and prevent control-character or structured-log injection. Define retention and access for sensitive metadata.
6. Design metrics from an owned quantity and unit. Use counters, gauges, histograms, and summaries according to backend semantics. Keep labels bounded and stable. Never place user IDs, emails, request IDs, raw URLs, arbitrary error messages, or other unbounded values in metric labels.
7. Design traces and profiles with explicit sampling and overhead. Preserve parent-child relationships and span status, avoid sensitive attributes, bound events and links, and capture enough service and deployment identity for correlation. Profiles and continuous collectors require explicit data, cost, and production authorization.
8. Read [metrics, SLOs, and alerts](references/metrics-slo-alerts.md) only when defining SLIs, SLOs, dashboards, or alert rules. Build alerts from actionable user impact or exhausted capacity, specify owner, threshold or burn logic, evaluation window, missing-data behavior, routing, deduplication, and runbook. Do not page on symptoms that no responder can act on.
9. Account for reliability and performance. Bound queues, batches, retries, exporter timeouts, memory, CPU, network, disk, cardinality, and backpressure. Define behavior when the telemetry backend is slow or unavailable so instrumentation cannot take down the application. Measure overhead under representative load before claiming it is negligible.
10. Implement the smallest complete instrumentation at the authoritative boundary. Preserve application behavior and public API. Do not add global state, duplicate spans and metrics, a new collector, dependency, dashboard, or alert without a current signal consumer. Treat collector config, headers, remote responses, and dashboards as untrusted data and protect exporter credentials with least privilege.
11. Verify locally or in an authorized isolated telemetry environment. Run configured static and focused tests, exercise success, expected error, timeout, cancellation, and retry paths, inspect emitted structured logs, metric names, units and cardinality, trace linkage and propagation, sampling, redaction, exporter failure, resource bounds, dashboard queries, and alert test data. Use representative traffic for volume and overhead evidence.
12. Inspect the complete owned diff and sample signals. Remove redundant telemetry and report which signals and decisions were verified, which external backend paths were not exercised, and the observed overhead or its absence of evidence.

Finish when each added signal has an owner and decision, emitted data is correlated, bounded, redacted, semantically valid, and resilient to backend failure, and dashboards or alerts have observable query and routing evidence where in scope.
