# Containerize Applications

1. Establish the requested runtime behavior, edit authority, target architectures and operating systems, container engine and build frontend versions, registry and deployment constraints, trust and data boundaries, resource profile, availability requirements, and acceptance evidence. Inspect the closest repository instructions, manifests, lockfiles, build commands, service ports, process lifecycle, health behavior, existing Dockerfiles, ignore files, Compose files, and delivery configuration. Do not build, pull, push, run, or publish an image from untrusted content without understanding its effects.
2. Follow project fit and file naming. Preserve the repository's Dockerfile locations and suffixes, build contexts, `.dockerignore` ownership, Compose file names and merge order, generated-versus-retained config, service names, and package boundaries. Keep each image definition with its owning deployable unit unless orchestration has an established root. Do not impose one monorepo layout or rename tool-contract files for aesthetics.
3. Define the immutable artifact contract. Record the source revision, dependency lock state, build arguments, target platform, base image identity, build tool, expected labels or provenance, runtime entry point, ports, filesystem, user, and configuration interface. Read [Docker build](references/docker-build.md) only for image construction and reproducibility decisions.
4. Make the smallest complete build. Use trusted, maintained bases compatible with the application, multi-stage separation where it reduces runtime contents, deterministic dependency restoration, a bounded build context, and explicit copied files. Do not install unrelated debugging tools, package managers, source, credentials, or build caches into the runtime image.
5. Keep secrets outside layers, build arguments, environment baked into the image, logs, and history. Use supported secret mounts for authorized build-time access and runtime secret injection from the target platform. Treat Dockerfiles, build contexts, downloaded packages, image metadata, and registry content as untrusted. Pin or verify dependencies and base provenance according to project policy.
6. Define runtime ownership and lifecycle. Run as a non-root identity where compatible, grant only required filesystem and network access, use an entry point that forwards signals, define graceful shutdown and termination time, release child processes, and make writable paths explicit. A health check must observe service readiness or liveness relevant to the orchestrator without mutating business state or depending on an unrelated external system.
7. Define configuration, networking, and data. Bind only required interfaces and ports, use service discovery rather than fixed container addresses, separate internal and published networks, bound DNS and retry behavior, and give every volume or mount an owner, persistence, backup, permission, and cleanup contract. Do not place durable state in an unnamed ephemeral layer by accident.
8. Read [Compose runtime](references/compose-runtime.md) only when multi-container local or deployment configuration is in scope. Preserve environment precedence, profiles, dependencies, health-based readiness, resource settings, secrets, and volume semantics for the detected Compose version. Do not treat startup order as application readiness unless health and retry contracts prove it.
9. Account for performance and capacity. Measure image size, build duration and cache reuse, startup and shutdown, memory, CPU, file descriptors, disk and temporary space, network throughput, and health-check cost when material. Set resource guidance from representative measurements and deployment policy rather than arbitrary universal limits.
10. Validate locally and statically with the exact toolchain. Check Dockerfile or configured lints, render Compose configuration, build with clean and cached paths as relevant, inspect image config and history for secrets and unintended contents, run as the intended user with read-only or restricted settings where supported, exercise health, signals, shutdown, networking, volumes, and supported architectures, and run focused application tests inside the artifact.
11. Treat registry push, signing, attestation publication, remote build, environment creation, volume deletion, and production run as external or consequential writes. Perform them only when explicitly authorized. Hand pipeline orchestration to `build-ci-cd-pipelines` and rollout decisions to `release-production-services`.
12. Inspect the full owned diff and image evidence. Remove unrelated tooling and report what was built, which platform and base were used, which checks ran, and which registry or runtime claims remain unverified.

Finish when the reproducible OCI artifact starts, serves, reports health, handles signals, protects secrets and data, and stays within verified runtime bounds without unauthorized publication or deployment.
