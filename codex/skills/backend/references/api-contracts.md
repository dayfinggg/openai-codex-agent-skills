1. Before editing, read route handlers, request and response schemas, the existing OpenAPI dialect, middleware order, callers, generated clients, and contract tests. Establish method, path, payload, accepted events, status codes, headers, and content negotiation. Trace touched transformations through persistence. Check encoding, nullability versus missing fields, pagination, idempotency, and version compatibility where affected.
2. Validate untrusted input at its owning boundary using the installed framework. Preserve distinctions among malformed input, unauthenticated requests, forbidden operations, hidden or missing resources, and internal errors where exposed by the contract. Check object, property, and function permissions server-side. Preserve deliberate resource-existence concealment. Return public-safe errors and retain diagnostic context through the existing logger.
3. Keep the existing error format unless changing it is requested. When using [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html), use the negotiated problem media type, stable problem types, and a matching HTTP status when the body includes `status`. Keep stack traces, internal paths, and secrets out of details. Do not silently replace a legacy envelope with problem details.
4. Update an existing contract artifact with the behavior change. Keep its declared [OpenAPI version](https://spec.openapis.org/oas/latest.html) and supported generator semantics. Review required fields, enum changes, defaults, serialization, and response projection against real consumers. Check operation-level security overrides and alternative versus combined security requirements. Do not create a new API version or unrelated documentation for a local fix. Resolve a genuinely incompatible requirement before dependent changes.
5. Verify through the real middleware path using a supported client request. Assert status, headers, body shape, persisted effects, and unchanged consumer behavior. Exercise malformed input, missing or invalid credentials, permission denial, and touched boundary cases. Rejected requests must have no forbidden effects. Test an unchanged legitimate request and a different user's or tenant's object where authorization is affected. Run the existing schema or client-generation check when that artifact changes, using its installed tooling.
6. Report the observable contract change, whether clients must adapt, and which success and rejection paths ran. Name any unresolved incompatibility or unverified consumer. Consult [OWASP API Security Top 10 2023](https://owasp.org/API-Security/editions/2023/en/0x11-t10/) for the affected risk, without turning the change into a full API audit.
