1. Before editing, establish the concrete threat, affected entry points, trust model, and legitimate users and events. Trace attacker-controlled values to queries, commands, paths, templates, deserialization, outbound destinations, and logs along the affected path. Read provider and framework documentation for the actual mechanism. Use relevant [ASVS 5.0.0 requirements](https://github.com/OWASP/ASVS) with version-qualified identifiers when citing a control.
2. For authentication, use the supported verifier and credential store. Check token integrity, configured algorithms, issuer, audience, lifetime, and session semantics as required by the existing token profile. Enforce the existing object, tenant, property, and operation authorization at the server boundary. Do not mistake a valid token or webhook signature for permission to access a user's resources. Follow the applicable [REST security guidance](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html).
3. For signed webhooks, verify the provider-defined signed bytes before effects. Inspect raw-body preservation, canonicalization, secret selection, timestamp tolerance, replay rules, and constant-time comparison or SDK verifier behavior. Test missing, malformed, invalid, and tampered signatures plus applicable stale and replayed requests. Preserve every supported event and intended error or acknowledgment behavior. [Stripe's signature guidance](https://docs.stripe.com/events/manage-webhook-endpoints#signature-errors) illustrates why parsed and reserialized bodies cannot substitute for the original signed input. Use the actual provider's rules rather than copying Stripe semantics universally.
4. For uploads, preserve authorized types and access while enforcing the existing business limits. Validate decoded filenames, content type and content signatures with supported parsers rather than trusting the supplied MIME header. Prevent traversal and executable storage, use safe generated storage names, and enforce size and decompression limits where applicable. Check download permissions and cleanup after failure. Apply relevant [file upload controls](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html) without silently reducing accepted file types.
5. For outbound requests, establish permitted destinations and internal-service needs first. Use supported URL parsing, constrain schemes and ports, and validate resolved IPv4 and IPv6 destinations at connection time. Prevent unauthorized loopback, private, link-local, and metadata access, including DNS rebinding. Disable redirects or validate every hop without forwarding credentials to another origin. Bound connection and response work through the existing client. Prefer established destination restrictions from [SSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html), without imposing a new user allowlist.
6. For injection, use parameterized queries and safe process APIs that avoid a shell. Keep user data out of executable templates, interpreter code, and unsafe deserialization. Use context-specific encoders when a safe parameterized interface is unavailable. Check paths after canonicalization against the intended storage boundary. Follow [injection prevention guidance](https://cheatsheetseries.owasp.org/cheatsheets/Injection_Prevention_Cheat_Sheet.html), not a generic character blacklist.
7. Verify authorized success, material rejection cases, and unchanged access and event behavior using isolated fixtures. Assert both response and forbidden side effects. Check all affected callers and equivalent routes so the protection is not confined to one entry point. Run existing project security checks and inspect candidate findings for a reachable data flow. Do not run destructive probes against live services or expand into a repository-wide audit.
8. Report the protected boundary and demonstrated attack condition, preserved legitimate behavior, and executed checks. Separate confirmed defects from suspicions and name unverified assumptions. Do not report stylistic preferences as vulnerabilities.
