1. Trace all readers and writers, the authoritative store, cache client, serialization, key builder, TTL, negative entries, invalidation and process-local caches. Establish allowed staleness, identity/tenant boundaries, consistency-critical state and behavior when each dependency fails. Diagnose the layer supplying stale bytes before changing cache TTLs.

2. Derive keys from every verified input affecting the value, including tenant/user or permission scope, query/filter/order/page, locale and representation/schema version when applicable. Normalize equivalent inputs without merging distinct ones. Authorize access before serving a hit. Do not trust a request-supplied tenant identifier merely because it appears in a key. Test the same logical object under different authorized users, tenants and permissions.

3. Choose cache-aside, write-through or the existing refresh mechanism from the contract. Retain the uncached result semantics, error types and authorization. Cache negative results only with an explicit short-lived policy that does not hide later creation or denied access. Keep missing, null, empty and cached-error states distinguishable. Bound payload size and support the existing serializer's types and rolling-release formats.

4. Trace commit, invalidation delivery and repopulation as one timeline. Publish invalidation after successful commit and avoid invalidating as though a rolled-back write succeeded. Cover every derived key or dependent result, including lists, aggregates and deletions. Account for duplicate, delayed, lost and out-of-order events when the architecture uses them. Do not introduce a queue or outbox unless the requested guarantee requires it.

5. Reproduce a stale-fill race by pausing a reader after it reads the old source value, committing a writer and its invalidation, then resuming the old reader's cache fill. Choose an existing version/generation check, coordinated fill/write protocol or other mechanism that satisfies the stated freshness guarantee. Invalidation after commit alone cannot prevent this race. A fixed second delete or an arbitrary delay is not proof of consistency. Coordinate through the authoritative version when strict freshness requires it.

6. Bound simultaneous misses using the project's single-flight or lease mechanism. Process-local coalescing covers only that process. Add bounded TTL jitter when synchronized expiry drives load and it fits the freshness ceiling. Decide what callers do during refresh, timeout and owner failure. Serve stale values only where allowed. Measure origin call count during a concurrent cold miss instead of inferring stampede protection from hit rate.

7. For a Redis lease, acquire with an unpredictable ownership token and expiry in one atomic operation. Release and renew only after atomically checking that token. Test lease expiration, a paused former owner, a replacement owner and a failed release. Prevent an old owner from publishing over newer data. Use fencing or authoritative conditional writes when required for correctness. A lease can reduce duplicate refreshes without guaranteeing single-writer correctness through partitions or failover. Retrieve exact command/script semantics for the installed Redis and driver from [SET](https://redis.io/docs/latest/commands/set/) and [Lua execution](https://redis.io/docs/latest/develop/programmability/eval-intro/). These references were checked against Redis Open Source 8.10.

8. Define separate policies for cache read failure, origin read failure, cache fill failure, invalidation failure and malformed/old payloads. Bound retries and fallback concurrency so a Redis outage does not overload the origin. Preserve correctness-critical Redis state instead of silently treating every failure as a miss. Decide how committed writes with failed invalidation become visible within the promised freshness bound. Never use FLUSHALL, FLUSHDB or a shared-prefix purge to fix one stale entry.

9. Verify a miss and hit return the same authorized value, then test update, delete, negative-to-present transition, expiry and relevant rolling-format compatibility. Add a deterministic stale-fill interleaving, concurrent misses and the failure paths changed by the task. Verify local-client-cache invalidations across reconnects if that layer exists. Use task-owned keys and a controllable clock or bounded expiry check. Fakes alone do not establish Redis atomicity or cluster behavior.

10. Report which consistency/freshness contract now holds in the exercised cases, evidence for user isolation and concurrent misses, and any required key-version rollout or targeted invalidation. Compare latency and origin load only over equivalent traffic and data. State untested failure modes when they are required for the claimed guarantee.

The concurrency-check design is informed by [FMCache, 2025, sections 5.1 and 5.2](https://arxiv.org/html/2510.08351v1). That paper coordinates metadata reads and writes using validity state and locking. Apply its explicit validity/concurrent-update question to tests here, without treating its switch-specific algorithm as a Redis consistency guarantee.
