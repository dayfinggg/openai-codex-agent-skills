1. Inspect server/client versions, enabled features, topology, client construction, key types, command sizes, TTLs, data ownership and persistence/eviction configuration. Determine whether Redis holds disposable cache entries, sessions, locks, idempotency state or durable work. An eviction policy safe for a cache can destroy correctness-critical data on the same instance. Use [Open Source version management](https://redis.io/docs/latest/operate/oss_and_stack/install/version-mgmt/) and the [8.10 release notes](https://redis.io/docs/latest/operate/oss_and_stack/stack-with-enterprise/release-notes/redisce/redisos-8.10-release-notes/) as the research baseline. These latest URLs move, so recheck the installed version before using new commands.

2. Choose the structure from operations and consistency needs. Use strings for scalar values or whole-object cache payloads, hashes for independently updated fields, lists for bounded ordered sequences, sets for membership, sorted sets for score/range access and streams for replayable consumer-group work. Pub/Sub is not replayable durable delivery. JSON, probabilistic structures, time series and vector sets require the actual deployed feature. Compare memory, command complexity and error/accuracy tolerance before choosing them. Retrieve syntax from [Redis 8.x data types](https://redis.io/docs/latest/develop/data-types/).

3. Keep the application's established key schema. Include environment, service, verified tenant/entity and format dimensions where required. Avoid collisions and unnecessary long or secret-bearing names. Use bounded container sizes and explicit units for TTLs. Set value and expiration atomically when an immortal intermediate value would be wrong. Check whether replacement preserves or clears TTL in the selected command, and distinguish a missing key from an existing key without expiry. Do not add TTL to durable state without a retention contract. See [Redis 8.x keyspace](https://redis.io/docs/latest/develop/using-commands/keyspace/) and [SET options and version history](https://redis.io/docs/latest/commands/set/).

4. Use the narrowest atomic primitive. Prefer a single conditional command over client-side read/modify/write. A pipeline reduces round trips and does not inherently provide atomicity. Check whether the installed client's pipeline enables transactions by default. Use WATCH with bounded conflict retries or a short Lua script when decisions depend on stored values. Inspect all transaction replies. Redis transactions and Lua isolation do not supply rollback of earlier successful writes after runtime errors. Validate predictable failure conditions before writes.

5. For Lua, pass accessed keys explicitly, keep execution bounded and avoid keyspace walks or unbounded container work. Handle missing script-cache entries after restart/failover, including the client's pipeline behavior. Prefer existing project script loading/function conventions. Test error and concurrency paths as well as success. See [Redis 8.x Lua execution](https://redis.io/docs/latest/develop/programmability/eval-intro/) and [transactions](https://redis.io/docs/latest/develop/using-commands/transactions/). For application lock correctness, also read [application caching](application-caching.md).

6. Reuse the client's supported pool or multiplexer and release resources at the owning lifecycle boundary. Isolate blocking consumers and protocol modes that occupy a connection. Bound blocking waits, connect/read deadlines, pool waits and retry budgets according to the caller's total deadline. A timeout can leave a write's outcome unknown. Do not automatically replay non-idempotent increments or queue operations. Bound pipeline batch sizes and check individual results. Client-side caching needs supported tracking, invalidation and reconnect behavior, not just an assumed RESP version.

7. Inspect keyspaces incrementally, with a bounded scan budget. SCAN-family iteration can duplicate elements, return empty pages and observe concurrent mutation, so do not treat it as a consistent snapshot or COUNT as a strict result cap. Avoid KEYS, huge HGETALL/SMEMBERS responses and complete list reads in production. Do not grant SCAN to a tenant on the assumption that ACL key patterns hide unrelated key names. For one key, read only the fields and range needed.

8. In Open Source Cluster, group keys sharing an atomic multi-key operation into the same hash slot using a meaningful entity tag. Do not tag all application keys together. Use a cluster-aware client for redirects, resharding and bounded retries. Ordinary independent pipelined commands may span slots when the client routes them. Cross-slot transactions and multi-key scripts are a different contract. Check the exact command's supported behavior. Cluster uses database zero, so do not rely on database numbers for tenant isolation. Replica reads can be stale and are unsuitable for strict read-after-write, balances or correctness-critical coordination. Replication acknowledgments do not by themselves establish strong consistency through failover. See the [Redis 8.x cluster specification](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/).

9. For durability changes, establish tolerated loss and recovery time, RDB/AOF policy, storage capacity, replication and backup ownership. Snapshots, AOF fsync and replication have different loss windows and failure modes. Preserve these settings on shared stores. Validate an authorized recovery change with restore/restart checks in an isolated target. Never disable persistence, run repair utilities or induce production failover merely to tune a cache. See [Redis 8.x persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/).

10. Preserve authentication and certificate validation, use TLS and trusted network access, and keep protected mode enabled. For requested access changes, constrain commands, key patterns and Pub/Sub channels to actual application needs. Deny destructive/admin operations to app principals without removing supported app operations. Prefer ACLs to renamed commands. Validate both allowed actions and prohibited cross-tenant/admin actions using the affected principal. Never place credentials in command arguments, examples or logs. See [Redis 8.x ACLs](https://redis.io/docs/latest/operate/oss_and_stack/management/security/acl/) and [security](https://redis.io/docs/latest/operate/oss_and_stack/management/security/).

11. Diagnose with relevant INFO sections, bounded SLOWLOG reads, key memory samples and existing latency evidence. Inspect memory/eviction, hit/miss counts, connection/rejection/churn, blocked-client purpose, replication and last successful persistence. Set thresholds from this workload and recovery contract, not fixed global percentages. A legitimate blocking consumer is not automatically a fault. Slowlog command time does not measure end-to-end network or pool wait. Avoid MONITOR, SLOWLOG RESET or global configuration changes just to gather cleaner evidence.

12. When maintaining existing Search behavior, preserve the following checks while retrieving syntax on demand from [Redis 8.x Search](https://redis.io/docs/latest/develop/ai/search-and-query/) and [query dialects](https://redis.io/docs/latest/develop/ai/search-and-query/advanced-concepts/dialects/).

- Match HASH/JSON storage, key prefix, field aliases and actual indexed types. Choose exact-match versus tokenized fields from semantics. Check indexing failures, document coverage and language/tokenization before rewriting a query. Do not broaden a literal filter because a guessed synonym returns results.
- Match command and result shape to retrieval, count, aggregation or hybrid ranking. Filtered KNN is not fused lexical/vector ranking. Check server/client capability, explicit dialect and escaping/parameter binding. Do not copy a benchmark's wording-to-command mapping or assume every dialect except two has been removed.
- Check aggregation stage inputs, aliases and output types. Apply index filters before materialization when equivalent, return needed fields, bound results and release cursors on completion, error and cancellation.
- Verify vector dimension, numeric encoding and distance metric against the actual model and storage. Choose exact versus approximate retrieval using required recall, corpus size and measured memory/latency, not a fixed vector-count cutoff. Test recall on representative expected matches and tenant filters.
- For an authorized schema replacement, build a new index, check backfill/coverage and query behavior, then switch the stable alias with a rollback path. Preserve source documents. FT.DROPINDEX with DD and equivalent client delete-document options delete data. TEMPORARY and SKIPINITIALSCAN have lifecycle/coverage consequences that require explicit review. Do not drop an existing live index to make creation idempotent.

13. Verify relevant type/TTL behavior, concurrent atomic updates, conflict/error outcomes, timeouts with unknown write results, reconnect and lifecycle cleanup. Exercise cluster routing only on a cluster and ACL changes using the real restricted role. Report observed results, topology, any changed retention/durability or access behavior, rollout needs and checks unavailable in the target environment.
