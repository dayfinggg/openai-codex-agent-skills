# TypeScript and JavaScript

Honor the repository's module system, runtime, target browsers, TypeScript version, `tsconfig`, package manager, formatter, linter, and test tools. Set compiler options deliberately. For a new TypeScript project, enable `strict` and relax individual checks only for an evidenced compatibility need. Do not treat a strict migration as complete until `noImplicitAny` is enabled unless the approved plan defines a staged intermediate state.

Prefer inference when the configured compiler determines the intended type accurately, and create related object properties together when that preserves inference. Use annotations to declare contracts rather than assertions to override the checker. Inspect an uncertain type with the editor, compiler, or `satisfies`-style check supported by the project instead of inferring it from appearance. Use `readonly` when it prevents mutation errors without misrepresenting runtime mutability.

Model domain states with precise object types and discriminated unions so invalid combinations are unrepresentable where practical. Prefer an explicitly imprecise type to a type that promises more than runtime behavior guarantees. Keep `any` within the narrowest possible scope, prefer `unknown` for untrusted or genuinely unknown values, and hide an unavoidable unsafe assertion behind a validated, well-typed boundary. Track type coverage only when the project uses a configured tool and threshold to detect a relevant regression.

Prefer `async` functions over callback orchestration when that improves type flow while preserving ordering, cancellation, and error semantics. Prefer standard ECMAScript features to TypeScript-specific runtime constructs unless the latter has a concrete benefit. Use `const` by default, explicit public contracts, coherent module ownership, and established platform APIs.

Avoid non-null assertions without a proved invariant, implicit coercion that obscures meaning, mutation shared across modules, unhandled promises, floating asynchronous work, and unsafe DOM insertion. Validate runtime data because static types do not validate network, storage, environment, or user input. Propagate cancellation with the platform's supported mechanism and preserve error causes. Select dependencies by maintenance, compatibility, security, and bundle or runtime cost. Do not mix CommonJS and ESM without an intentional interoperation boundary.

Primary references: [TypeScript Handbook](https://www.typescriptlang.org/docs/handbook/intro.html), [everyday types](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html), [narrowing](https://www.typescriptlang.org/docs/handbook/2/narrowing.html), [strictness](https://www.typescriptlang.org/tsconfig/strict), and [MDN JavaScript](https://developer.mozilla.org/docs/Web/JavaScript).
