# TypeScript and JavaScript

Honor the repository's module system, runtime, target browsers, TypeScript version, `tsconfig`, package manager, package scripts, `.editorconfig`, Prettier configuration, ESLint configuration, formatter, linter, and test tools. Run the configured package script through the repository's package manager before invoking a binary directly. When Prettier is a declared local tool, use its check mode, such as `pnpm exec prettier --check path/to/file.ts`, with repository configuration and ignore files. Run ESLint separately because formatting does not replace linting. Do not download or select Prettier or ESLint for a repository that has not adopted them.

When repository policy is absent but a declared Prettier has no explicit options, accept its defaults: two-space indentation, spaces rather than tabs, and an 80-column `printWidth`. `printWidth` is a wrapping target, not a maximum. When no formatter is selected, use two spaces and no tabs as this skill's local JavaScript-family fallback, then apply the line-width row and every function, class, file, nesting, complexity, and parameter threshold from [code shape and naming](code-shape-and-naming.md). This fallback is not an ECMAScript or TypeScript language standard.

Follow framework and neighboring-file naming first. If none exists, use this local fallback: `camelCase` for variables and functions, `PascalCase` for classes, interfaces, type aliases, enums, and component identifiers, and `UPPER_SNAKE_CASE` only for project-level constants that are treated as constants. JavaScript and TypeScript do not define a universal filename case. Use [project structure and file roles](project-structure-and-file-roles.md) for framework-special files and role suffixes. Otherwise use descriptive lowercase kebab-case module filenames, retaining `PascalCase` only where a component-centered package already uses it. Preserve `.d.ts`, module-mode extensions, package exports, route names, and test-discovery suffixes.

Set compiler options deliberately. For a new TypeScript project, enable `strict` and relax individual checks only for an evidenced compatibility need. Do not treat a strict migration as complete until `noImplicitAny` is enabled unless the approved plan defines a staged intermediate state.

Prefer inference when the configured compiler determines the intended type accurately, and create related object properties together when that preserves inference. Use annotations to declare contracts rather than assertions to override the checker. Inspect an uncertain type with the editor, compiler, or `satisfies`-style check supported by the project instead of inferring it from appearance. Use `readonly` when it prevents mutation errors without misrepresenting runtime mutability.

Model domain states with precise object types and discriminated unions so invalid combinations are unrepresentable where practical. Prefer an explicitly imprecise type to a type that promises more than runtime behavior guarantees. Keep `any` within the narrowest possible scope, prefer `unknown` for untrusted or genuinely unknown values, and hide an unavoidable unsafe assertion behind a validated, well-typed boundary. Track type coverage only when the project uses a configured tool and threshold to detect a relevant regression.

Prefer `async` functions over callback orchestration when that improves type flow while preserving ordering, cancellation, and error semantics. Prefer standard ECMAScript features to TypeScript-specific runtime constructs unless the latter has a concrete benefit. Use `const` by default, explicit public contracts, coherent module ownership, and established platform APIs.

Avoid non-null assertions without a proved invariant, implicit coercion that obscures meaning, mutation shared across modules, unhandled promises, floating asynchronous work, and unsafe DOM insertion. Validate runtime data because static types do not validate network, storage, environment, or user input. Propagate cancellation with the platform's supported mechanism and preserve error causes. Select dependencies by maintenance, compatibility, security, and bundle or runtime cost. Do not mix CommonJS and ESM without an intentional interoperation boundary.
