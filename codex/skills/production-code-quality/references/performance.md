# Performance engineering

Use this reference only for an explicit optimization, a performance regression, a measured hot path, materially growing data, or a stated latency, throughput, memory, I/O, energy, or cost constraint. Do not turn an ordinary change into a benchmark project or claim an improvement from code appearance.

1. Define the user-visible or operational outcome, metric, budget, representative workload, data distribution, concurrency, environment, correctness oracle, and resource ceilings. Include input growth when algorithmic complexity or capacity is material.
2. Establish a correct baseline before editing. Record hardware, OS, runtime, compiler, build flags, dependency versions, dataset, cache state, background load, and benchmark command. Confirm that the load generator and measurement path have headroom.
3. Locate the limiting resource with a profiler, trace, query plan, allocation report, counter, or complexity analysis. Distinguish CPU, waiting, locking, allocation, storage, network, serialization, downstream capacity, and measurement overhead instead of guessing.
4. Change the smallest evidenced bottleneck. Prefer an existing path, language feature, standard library, or installed dependency before adding caching, batching, pooling, parallelism, denormalization, native code, or a new package. Define invalidation, bounds, ordering, and failure behavior for any stateful optimization.
5. Preserve functional equivalence before measuring speed. Exercise normal, boundary, and material failure cases outside the timed region. Do not skip work, memoize a fixed benchmark answer, move work outside the measured interval, or tune only the visible fixture.
6. Design a comparable experiment. Apply appropriate warm-up, run multiple independent repetitions, and randomize or interleave baseline and candidate when drift is plausible. Choose the repetition count from observed variance rather than a fixed ritual. Use isolated processes, stable affinity, or controlled services when the platform and expected effect require them.
7. Report absolute results, relative change, repetitions, and variation. Use median and relevant tail percentiles for latency, throughput together with saturation and errors, and peak memory, allocations, GC, I/O operations, or cost when the optimization can trade one resource for another. Use a confidence interval or another uncertainty estimate when noise could change the decision.
8. Repeat on an independent representative workload and verify recovery after stress when applicable. Reject a result that does not reproduce, is indistinguishable from noise, changes correctness, moves the bottleneck to an unacceptable resource, or depends on a benchmark-only shortcut.
9. Add a stable regression benchmark, budget gate, or production signal only when the risk will recur and the environment can produce a meaningful signal. Otherwise preserve the command, workload, environment, raw measurements, and limitations needed to repeat the comparison.

Never report a speedup from incomparable builds, different datasets, different correctness, a single timing, or an unrecorded environment. If a stable benchmark is unavailable, report the optimization as unverified and do not claim the affected performance property.

Primary basis: [Google Benchmark user guide](https://google.github.io/benchmark/user_guide.html), [Google SRE monitoring distributed systems](https://sre.google/sre-book/monitoring-distributed-systems/), [Brendan Gregg's performance methodology](https://www.brendangregg.com/methodology.html), and the benchmark-design evidence in [PERFOPT-Bench](https://arxiv.org/abs/2607.07744) and [Are Performance-Optimization Benchmarks Reliably Measuring Coding Agents?](https://arxiv.org/abs/2607.01211). The 2026 papers are preprints and motivate reproducibility and independent correctness checks rather than fixed universal sample counts.
