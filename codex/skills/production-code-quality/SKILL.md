# Production Code Quality

1. Establish the changed surface before choosing conventions. Inspect only the repository instructions, source and tests, nearby patterns, manifests and lockfiles, target configuration, and formatter, analyzer, compiler, or test settings that can affect the in-scope code. Identify only the language, framework, runtime, platform, and tool versions that affect that surface; do not inventory unrelated packages or subprojects.
2. Classify only the quality attributes the changed path can materially affect, such as correctness, compatibility, security, accessibility, performance, memory, concurrency, cancellation, availability, migration, rollback, and operations. For each affected attribute, record the relevant constraint or failure mode and the observable check that can detect a regression. Do not add process or machinery for an unaffected quality.
3. For every language with added or modified retained source, read its applicable language reference: [Python](references/python.md), [TypeScript and JavaScript](references/typescript-javascript.md), [Go](references/go.md), [Rust](references/rust.md), [Java and Kotlin](references/java-kotlin.md), [.NET](references/dotnet.md), [C and C++](references/c-cpp.md), or [Swift](references/swift.md). Read [other languages](references/other-languages.md) and current official documentation for each unlisted affected language. Do not load guides for languages outside the changed surface.
4. Assess the local quality baseline before preserving conventions. Keep compatible, deliberate conventions, but do not reproduce unsafe, obsolete, inconsistent, or unmaintainable patterns. In a low-quality codebase, make new code and each touched responsibility a clean local precedent. Improve adjacent code only when correctness, cohesion, or reliable verification requires it. Preserve behavior and compatibility, keep the diff bounded, and expand into unrelated debt only with explicit approval. For a new project, select maintained stable tooling and official defaults for the target environment.
5. For a poorly understood or legacy area, read [legacy change](references/legacy-change.md) before changing behavior. Establish a characterization baseline and a testable seam when needed.
6. Design precise names, cohesive units, explicit contracts and ownership, simple control flow, deliberate error handling, minimal dependencies, and the smallest public surface. Introduce a pattern only for a concrete force it resolves. Treat size as a design signal, not a universal line limit. Split code when responsibilities, reasons to change, branching complexity, reviewability, or testability demand it; obey configured numeric limits when present.
7. Load specialized guidance only when its trigger applies. Read [performance](references/performance.md) for explicit optimization, a performance regression, a hot path, materially growing data, or a latency, throughput, memory, I/O, or cost budget. Read [concurrency and resilience](references/concurrency-resilience.md) when changing shared mutable state, asynchronous or background work, queues, networking, distributed coordination, retries, or resource lifecycle. Read [API contracts](references/api-contracts.md) when adding, upgrading, or depending on an external package, SDK, protocol, or version-sensitive API whose exact contract is material.
8. Read [security](references/security.md) only when the change creates, crosses, or alters one of these: a trust boundary; authentication, authorization, or permissions; secrets; sensitive data; untrusted input; output encoding or rendering; files or archives; processes or commands; cryptography; dependencies; or build, release, and deployment handling. Read [testing](references/testing.md) when selecting or changing test strategy. Read [compatibility](references/compatibility.md) when changing a public API, library, protocol, schema, persisted format, event, command line, configuration, deployment contract, or supported environment. Use a specialized process only when its trigger applies; this skill does not require unrelated skills.
9. Implement completely, then run the configured formatting, analysis, compilation, tests, build, and relevant runtime checks. Use [sources](references/sources.md) when a durable engineering source is needed to guide a trade-off or substantiate a recommendation.

Finish when changed code meets the configured project rules and applicable current language guidance in proportion to its risk, every changed contract and affected quality attribute has observable evidence, and no material quality gate remains unrun without an explicit reason. Report legacy constraints that prevent the touched area from meeting that bar.
