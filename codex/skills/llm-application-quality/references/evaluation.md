# Evaluation

1. Preserve a versioned dataset of real, anonymized, or faithful synthetic tasks. Include common cases, hard cases, boundary conditions, expected abstention, adversarial inputs, composed workflows, and cases where retrieval, tools, or agents must not activate.
2. Define the oracle before the run: required result, acceptable variants, forbidden behavior, required evidence, deterministic checks, grader, repetitions, aggregation rule, practical threshold, non-inferiority margin, and decision rule. Do not derive the oracle from the candidate output.
3. Keep baseline and candidate conditions comparable: model and snapshot or alias, reasoning effort, prompts, tools, permissions, data, indexes, repository revision, environment, timeouts, and token or cost limits. Change one attributable block unless the components cannot function independently.
4. Treat safety, permission, data-integrity, required-contract, and irreversible-effect cases as must-pass. When code or configuration changes, also require no invented API or dependency, no unjustified public surface, no weakened test, and no failure of the applicable compatibility case. Use hidden or independently authored composed cases where visible component tests can be gamed.
5. Measure end-to-end task success first. Add factual support, citation entailment, retrieval recall and relevance, tool-call validity and success, stop behavior, unsafe effects, unnecessary concepts and actions, latency distribution, token use, and cost only where they represent the contract.
6. Separate component failures. A good final answer does not excuse failed retrieval or an unauthorized tool attempt. Strong retrieval does not prove grounded generation. A valid schema does not prove the external postcondition. A smaller diff does not excuse a correctness or compatibility regression.
7. Repeat nondeterministic cases according to a fixed rule and retain raw outputs, tool traces, errors, grader reasons, and raw measurements. Blind human review should resolve subjective style or usefulness judgments and inspect high-consequence cases.
8. Compare performance only on the same correct workload and environment with a predefined repetition and aggregation rule. Report variation. Treat a noisy or non-reproducible apparent improvement as inconclusive, and do not trade correctness or a required contract for lower latency, tokens, or cost.
9. Accept a candidate only when it clears every must-pass gate, meets the practical improvement threshold, and causes no material regression in a required segment. Preserve the exact baseline artifacts and configuration plus a direct rollback path, then verify the focused regression set after any deletion pass.

Do not optimize to one grader, use model confidence as factual proof, infer success from a single demonstration, or count lower tokens, fewer tools, less code, or a higher benchmark score as success when task quality declines.
