1. Read project rules and recent substantive messages for the affected area with `git --no-pager log --no-merges`. Preserve the established language, prefixes, capitalization and commitlint rules. Without a local convention use the task's language and a concise imperative subject naming the actual change. About 50 subject characters and 72 body columns are readability conventions, not Git validity requirements. Keep required literals and URLs intact.
2. Separate any body with a blank line. Explain the original problem, resulting behavior and material reason or tradeoff. A simple change may need only a subject. Remove diff narration, conversation history, unsupported benefits and discarded alternatives that do not explain the final implementation. Compare every factual claim with the prospective commit.
3. Use [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) only when requested or established locally. Follow `type(scope): description`, with optional scope, feat for features and fix for bug fixes. Other types follow project policy. Mark genuine incompatible changes using ! or the required BREAKING CHANGE footer and explain the incompatibility. A documentation correction does not establish an application behavior change.
4. Include issue references and trailers only with verified facts and a valid basis. Close an issue only if the change resolves it. Signed-off-by is a contributor certification, distinct from a cryptographic signature. Do not add it on another person's behalf. Do not invent reviewers, coauthors, checks or measurements.
5. For a PR describe the concrete problem and final user-visible behavior, then executed validation and material limitations. Respect the repository template and scale detail to the change. Rewrite title and body when the final scope changes. Do not copy conversational history. Prefer structured body fields or a task-owned UTF-8 body file to shell-interpolated multiline text, and remove the temporary file afterward.
6. Review the saved message against the actual final diff. The reader must understand the change without the chat. Follow [Git's contribution guidance](https://git-scm.com/docs/SubmittingPatches) for its explanatory principles without imposing Git-project-specific conventions on other repositories. Check [GitHub skip-run behavior](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/skip-workflow-runs) only when notification or CI suppression is explicitly relevant.
