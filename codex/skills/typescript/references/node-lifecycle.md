1. Read the launch command, framework lifecycle, deployed Node version, HTTP limits, middleware order, dependency clients, and shutdown mechanism. Identify the owner of each request, deadline, cancellation signal, timer, socket, file, cursor, and pool.
2. Distinguish a total deadline from connection, header, body, idle, and keep-alive timeouts. A Promise.race only stops waiting. For node:http, a timeout option or setTimeout emits a timeout event without aborting the request. Connect the supported abort or destroy mechanism to the operation and propagate cancellation into supporting dependencies.
3. Handle pre-aborted signals, abort during work, late completion, and settlement races without duplicate responses or unhandled rejections. Remove task-owned listeners and timers on every terminal path. Do not cancel a shared operation still needed by another consumer.
4. Preserve streaming backpressure. Use the existing pipeline mechanism or honor a false write result before writing more. Handle upstream failure, client disconnect, partial output, and disposal of files or cursors. A pipeline can destroy an HTTP socket on error, so establish whether a fallback response remains possible before sending it. Do not buffer an entire stream or raise limits to hide a failure.
5. Consume or cancel response bodies through the deployed client's documented mechanism so connections can be reused. Keep cleanup separate from the success response. Preserve the original error when cleanup also fails.
6. Check uncaught exceptions and rejected promises against deployed runtime behavior. Do not return success for failed work or resume a process whose state is invalid. Do not add retries, middleware, or global signal handlers unrelated to the requested behavior.
7. On shutdown, stop admission, drain active work, then close owned pools and other handles within the configured deadline. Check long-lived or upgraded connections separately. server.closeAllConnections can terminate active HTTP connections and does not close upgraded WebSocket connections. Do not use it as the first graceful-drain step.
8. Keep work required for request success inside the completion boundary. Post-response work needs the existing supported lifecycle or durable job path. A detached promise is not a delivery guarantee. Signal handling and exit must not truncate pending output or cleanup.
9. Exercise the original scenario and affected dependency-failure, client-disconnection, deadline, and shutdown paths with bounded tests. Check real cancellation and handle release, not only a rejected wrapper promise. Correlate durations and failures with logs. Include a normal success case to detect changed response behavior.
