Read when a Symfony request, profiler token, log context, dependency-injection binding, or environment variable loading is the diagnostic entry point.

1. Establish Symfony and PHP versions, application environment, serving runtime, and request identity. Use installed project tools, including Symfony Mate when available, after checking their discovered schema or local help. Do not install Mate or enable production diagnostics just to follow this procedure. Keep tool/runtime failures separate from application failures.

2. Go directly to container inspection for missing services, wrong injected implementations, inactive tags/listeners, or decorators. For a known request with a matching profile, use that profile. For history, frequency, or cross-request behavior, use logs. If no source is known, check once for a matching profile, then fall back to logs. Logs may themselves be disabled, inaccessible, or outside retention.

3. For a profile, verify token, URL, method, timestamp, and environment. JSON responses can carry `X-Debug-Token-Link` without an HTML toolbar. Read the collector inventory before selecting collectors. A metadata lookup need not contain that inventory. Start with exception details for errors, time then database and memory for latency, request data for wrong output, and request-scoped logger data for correlation. Follow parent/subrequest relationships. An error response without an exception does not prove an upstream defect. Check request status, logger, and error handling first.

4. Distinguish repeated grouped SQL and query count from one slow statement using call counts and average/total time. Do not identify N+1 from duplicate text alone. Inspect truncation flags before claiming completeness. A missing collector is different from an empty collector. A stale token or cleared storage needs a new matching profile or log fallback. Never enable the profiler in production.

5. Locate configured Monolog handlers, destinations, channels, thresholds, rotation, and environment before searching. Default development logs use `var/log/dev.log`; production can use stderr rather than a file. Bound searches by time, level, channel, and request/context identity. A tail of the newest file cannot cover rotated history. Exact level or channel filters may hide matches. When a search is empty, check those filters and the destination before concluding no event occurred. A returned log file line number is not automatically an application source line. Read request-scoped logger data when available even if a file handler is quiet.

6. Inspect the compiled container for the correct environment, not whichever dump a tool finds first. In Symfony 7.4 and 8.1, use `php bin/console debug:container` with an exact service ID or exact tag filter and the intended environment. Confirm local help before invocation. Avoid a whole-container dump. Resolve aliases to the actual implementation, then inspect arguments, tagged collections, factory, setter calls, visibility, sharing, lazy/synthetic/abstract flags, and decorators. Check autowiring, autoconfiguration, resource exclusions, attributes, event names, and priorities against source configuration.

7. Distinguish a missing compiled dump from a filter with no matches. Compile or warm a container only in an authorized environment. If a warm container cannot be parsed, inspect the tool's runtime and required extensions. Empty constructor arguments may be valid for a synthetic or no-argument service; inspect setter calls. Do not treat a tool's stripped leading dot or resolved alias as a universal Symfony ID rule. Narrow truncated service results instead of increasing limits blindly.

8. For environment loading, inspect declarations, parsing, precedence, dumped `.env.local.php`, runtime overrides, and the process that actually boots Dotenv. Compare CLI and serving processes without dumping values. Missing optional `.env.local` files can be normal. Distinguish declared-empty, unresolved-in-this-process, ambient-only, override, and entirely unset states. Mate may not boot the application's Dotenv, so its unresolved state alone does not establish an application failure. Never reconstruct masked previews.

9. Do not send raw output from `debug:dotenv` or `debug:container --env-vars` into tool transcripts because these commands display values. Prefer an existing redacted project diagnostic or inspect variable names, source files, and presence through a value-suppressing interface. If safe output is unavailable, state the missing check instead of exposing a secret. Verify a correction through the original request or service resolution in the same environment.

Official guidance covers [profiling](https://symfony.com/doc/8.1/profiler.html), [logging](https://symfony.com/doc/current/logging.html), [container inspection in 7.4](https://symfony.com/doc/7.4/service_container.html), [container inspection in 8.1](https://symfony.com/doc/8.1/service_container.html), and [environment precedence and diagnostics](https://symfony.com/doc/7.4/configuration.html). Select the installed version instead of assuming current documentation applies.
