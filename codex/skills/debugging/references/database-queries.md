Read when actual SQL, lock waits, or connection exhaustion accounts for the reported latency or throughput defect.

1. Identify engine, server version, database, role, interval, query fingerprint, bound parameters, expected result grain, and transaction boundaries. Separate connection-pool checkout, network time, database execution, and application materialization. Inspect relevant schema, constraints, indexes, statistics, and callers.

2. Start with a plain plan for the representative statement. Before `EXPLAIN ANALYZE`, inspect side effects and execution cost because it runs the statement. Use a safe representative environment when execution exceeds authorization. A rollback is not a universal safeguard for external effects, sequence consumption, or load. Bound diagnostic execution using the engine's version-matched timeout facilities.

3. Compare estimates and actual rows, loops, filters, access paths, sorts, hash spills, buffers, and wait events where supported. Do not call a sequential scan or filesort a defect on its own. For locking, identify waiter, blocker, transaction age, lock ordering, and application retries. For connections, distinguish pool size, checkout leaks, long transactions, and server saturation. Do not terminate sessions or broaden production scans merely to simplify diagnosis.

4. For PostgreSQL 18, inspect `pg_stat_activity` for state, transaction start, and wait events. Correlate `pg_locks` with activity and use `pg_blocking_pids(pid)` for blocker identity rather than assuming every ungranted lock has a simple relation-level blocker. Restrict the inspection to the affected database and sessions. Privilege-limited query text is unavailable evidence, not proof of inactivity.

5. If `pg_stat_statements` already exists, compare interval deltas of `calls`, `total_exec_time`, and `rows` for the same database, user, and `queryid`. Check reset time and entry eviction before interpreting deltas. Normalized statements hide parameter-specific behavior, so inspect representative binds separately. Do not reset shared statistics or restart PostgreSQL to enable this extension during diagnosis. Adding it to `shared_preload_libraries` requires a restart and needs a separately authorized operational change.

6. For MySQL 8.4 LTS or 9.7, use the matching manual's `EXPLAIN` and `EXPLAIN ANALYZE` formats rather than copying PostgreSQL options. In 8.4, analyzed plans use `TREE`. Read `performance_schema.data_lock_waits` for requesting and blocking transaction/thread identities and join their lock IDs to `data_locks` for details. Inspect metadata lock waits separately when no InnoDB data-lock edge explains the stall. Missing instrumentation or privileges is not absence of contention.

7. Test the smallest supported query, index, statistics, transaction, or pool correction. Account for index write cost, parameter sensitivity, and other consumers of shared objects. Compare equivalent data, inputs, concurrency, and cache conditions before and after. Verify returned row identity, ordering, and required multiplicity as well as latency. Use the installed engine's procedure for MongoDB or Redis instead of applying SQL diagnostics to them.

PostgreSQL 18 documents [EXPLAIN](https://www.postgresql.org/docs/18/using-explain.html), [statement statistics](https://www.postgresql.org/docs/18/pgstatstatements.html), [locks](https://www.postgresql.org/docs/18/monitoring-locks.html), [activity](https://www.postgresql.org/docs/18/monitoring-stats.html), and [blocker functions](https://www.postgresql.org/docs/18/functions-info.html). MySQL documents plans for [8.4](https://dev.mysql.com/doc/refman/8.4/en/explain.html) and [9.7](https://dev.mysql.com/doc/refman/9.7/en/explain.html), and [data lock waits](https://dev.mysql.com/doc/refman/9.7/en/performance-schema-data-lock-waits-table.html). Read the deployed major version's sections before using its fields or options.
